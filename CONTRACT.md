# TierYourLife proxy: the contract

The one description of what the proxy answers, read by the website and by the Android app. It is written from `functions/src`; where this file and the code disagree, the code is right and this file has a bug.

> **Rule.** A PR that changes a request or a response shape (a path, a method, a field, a status, an error `code`, a limit, a cursor) updates CONTRACT.md in the same PR. `functions/test/contract.test.ts` fails when a path word the routers answer is missing here, and when an exported function is not named here.

## Conventions

**Base URL.** Every function is in `europe-west1`: `https://europe-west1-tieryourlife.cloudfunctions.net/<function>`. A path after the function's name is the route. Behind Hosting the function's own name arrives as the first segment as well (`/lists/lists/mine`); `lists`, `boards` and `tmdb` accept both forms, so `/lists/mine` and `/lists/lists/mine` are the same route. Below, routes are written as `/<function>/<route>`.

**Access.** Each route says which of these it needs:

| Word | Means |
|---|---|
| App Check | `X-Firebase-AppCheck: <token>`. Missing or invalid: `401 APP_UNVERIFIED`. Checked first on every function, except that `generate` says `GENERATION_OFF` before it. |
| user | `Authorization: Bearer <Firebase ID token>`, a guest's (anonymous sign-in) included. Missing or invalid: `401 UNAUTHENTICATED`. Every route of `lists`, `boards`, `credits`, `adoptGuestCredits`, `generate` needs it. A write (any method but `GET`, `HEAD`, `OPTIONS`) with a token whose uid was erased since (`DELETE /boards/account`), a guest's token from before it linked a provider included, gets **`401 ACCOUNT_ERASED`**, on every function, before anything is read or written; `503 UNAVAILABLE` when that cannot be checked. Reads go on and find nothing. |
| account | A user whose sign-in provider is not `anonymous`. A guest gets `403 NOT_SIGNED_IN` unless the route says otherwise. |
| not banned | An account without a live ban, its own (`bans/{uid}`) or one kept from an account the same person erased (`bannedIdentities`, see `DELETE /boards/account`): else `403 {error, code: "BANNED", until}` (`until` is epoch ms, or `null` for forever; of two bans, the one that lifts last). |
| staff | The owner or a moderator. Else `403 NOT_YOURS`. |
| owner | The owner alone: the account whose uid is `MODERATOR_UID` or whose verified e-mail is `MODERATOR_EMAIL`. A moderator gets `403 {code: "NOT_YOURS", detail: "owner_only"}`, anybody else `403 NOT_YOURS`. |

**Errors.** A refusal is JSON `{error, code, detail?}`: `error` is English for logs, `code` is what a client branches on. A few old refusals carry no `code`: `405 {error: "Use GET…"}` for a wrong method, `400 {error: "Which list?"}` / `"Which board?"`, `404 {error: "No such address"}` on `boards`, `400 Empty prompt` / `Prompt too long` on `generate`, and `tmdb`'s `404 Unknown path` / `502`. Any error the code did not expect is `503 UNAVAILABLE` on `lists` and `boards`.

**Caching.** Every answer of every function here, a refusal or a missing board included, carries `Cache-Control: no-store` (since 22.11.2026). Before, only the successful answers of most routes did, and Hosting's CDN kept a `404` of `GET /boards/{uid}` for ten minutes, also for the request after the board was written. A route's own `no-store` below is the same rule.

**Times** are epoch milliseconds. **Colours** are `#RRGGBB`. **Text** is collapsed (runs of whitespace become one space), trimmed, and cut to its limit rather than refused, unless a limit says it refuses.

**Ids.** A list id or topic id is `[A-Za-z0-9_-]{1,64}`. A section id is `[a-z0-9][a-z0-9_-]{1,39}`. An author uid for follows is `[A-Za-z0-9]{8,128}`. A picture id (a file in the caller's `users/{uid}/pictures/` in Storage) is `[A-Za-z0-9_-]{1,64}`.

**Locales.** Sections and topics carry `names` keyed by `en uk ru es pt-BR de fr pl tr ja ar`. House-list translations are keyed by the same set without `en`.

**Built-in sections**, in their order: `anime`, `film_tv`, `games`, `music`, `books`, `food`, `sport`, `people`, `other`. They are made the first time anything reads sections, and `other` is always last and never hidden.

## Public image addresses

In `lists` JSON responses, image fields (including covers, cards, preview images,
section/topic pictures, collages and author faces) use the existing absolute
`https://tieryourlife.com/img/original/{published|avatars|sections|topics}/{id}/{picture}`
address for recognized public objects in `tieryourlife.firebasestorage.app`
(`https://tieryourlife.web.app/img/original/…` until 20.11.2026). Requests may
still send the site's earlier addresses (`tieryourlife.web.app`,
`tieryourlife.firebaseapp.com`, `www.tieryourlife.com`): they are read as the
same picture.
This lets older Android image loaders display them when Storage requires App
Check. Other image hosts remain unchanged. `users/` and pending `proposals/`
never become public addresses; their existing authentication/token and visibility
rules still apply. This does not add a Proxy route or relax Storage rules.

Old Firebase `alt=media` addresses and these site addresses are accepted on
republish and refer to the same stored picture, copy source, cleanup name and
ranking card identity. Stored snapshots keep canonical Storage addresses; reads
do not migrate documents. IDs, titles and credits are unchanged. Boards answer
canonical Storage addresses, their shared catalogue copies included
(`published/catalogue/{picture}`, which the site serves as
`/img/original/published/catalogue/{picture}`).

**Cover focus** (since 15.11.2026). Which part of a single cover picture shows: a board's and a published list's `coverFocus` (its `coverImageUrl` or `coverPictureId`, never the `coverImageUrls` collage), a topic's and a section's `pictureFocus`. **CoverFocus** `{x, y, zoom}`: `x` and `y` the point of the picture that sits in the middle of the frame, as fractions of its width and height (0 left/top to 1 right/bottom), `zoom` how far in past the largest crop the frame allows, 1 to 4; all three finite numbers, kept exactly as sent, other keys left out. Anything else is `400 {error, code: "INVALID"}` (a board or a list: `error` begins `coverFocus: `; a topic or a section: `detail: "pictureFocus"`, `error` "A focus is {x, y, zoom}: x and y from 0 to 1, zoom from 1 to 4"). `null` or no field is the default: the centre `{x: 0.5, y: 0.5, zoom: 1}`, or for a tall picture (height / width strictly more than 1.2; since 15.11.2026) `{x: 0.5, y: 0.35, zoom: 1}`, where a portrait's face and a poster's title usually are (`defaultFocus`, `TALL_RATIO`). Every cover from before shows by it, so old clients keep working and show about what they did. A card's picture has the same field, `pictureFocus` on the card of a board and of a publication, cut by the same formula for the card tile (0.71), the collage cells and the large view. A feed card's collage: **ListSummary** `previewFocus` (since 15.11.2026), beside `previewImages` one for one, each the `pictureFocus` of the first card showing that picture or `null`, left out when none has one; a board's collage (`coverImageUrls`) is cut by the focus of the board's own card with that picture, which the client already has. A response carries the field only when there is a focus and a picture to apply it to. Every client cuts the picture for each frame it shows it in, with that frame's aspect A (width / height): for a W x H picture, if W/H > A the crop is H·A x H, else W x W/A; both sides divided by `zoom`; left = clamp(x·W − width/2, 0, W − width), top = clamp(y·H − height/2, 0, H − height); the crop is scaled to fill the frame. `functions/test/cover-crop-vectors.json` holds the shared cases (W, H, A, focus or none → crop, tolerance 1e-6; tall pictures without a focus among them), the defaults, and the focus values taken and refused; `cropOf` in `coverFocus.ts` is checked against it, and the Web and Android tests copy it unchanged. Example: a 1000 x 1500 portrait with `{x: 0.5, y: 0.15, zoom: 1}` in a 16:9 header is cut at `{x: 0, y: 0, width: 1000, height: 562.5}`, the head kept, where no focus (that tall picture's default, y 0.35) cuts it at `y: 243.75`.

## `lists`

All routes: App Check and user. `lists` keeps one instance warm.

### Feed and reading

**`GET /lists`**: the feed. Query, all optional:
- `category`: a section id; anything else means no filter.
- `author`: a uid. An anonymous list never appears on its author's page.
- `topic`: a topic id. With a topic, `category` is ignored (since 14.11.2026): a topic decides its lists' section itself, so the website (which sends both) and the app (which sends the topic alone) are shown the same lists, in the same order.
- `q`: search words (lower-cased, cut to 80). A list matches when its search keys hold every word; keys cover the title in every language once the search sweep has run. A `q` with no usable word answers `{lists: [], nextCursor: null}`.
- `sort`: `recent` (default, by `updatedAt`) or `popular` (by `takeCount`; since 23.11.2026 lists taken as often go by `updatedAt`, newest first, instead of by document id).
- `following=1`: only lists by followed authors, followed topics and followed sections (an anonymous list arrives by topic or section, never by author).
- `after`: the `nextCursor` of the page before.

Answer `200 {lists: ListSummary[], nextCursor: string | null}`, plus `followingNobody: true` when `following=1` and the caller follows nothing. Lists under review are left out, and so are lists waiting for approval (**Approval before the feed** below). **Cursor:** without `following=1` it is the last list's id; with it, `"<updatedAt or takeCount>:<id>"`. A short page is the last; a full page may be followed by an empty one. `409 CURSOR_GONE` when the list an id cursor names was taken down meanwhile: start again from the top.

**`GET /lists?fresh=1`** (since 23.11.2026; how clients show it revised the same day, `_coordination/community-order-2026-11-23/DECISION.md`, «Пересмотр 23.11»): people's new lists, shown **on top of Popular** on the website's home and in the app's Popular chip, marked «New». Every other parameter is ignored. Answer `200 {lists: ListSummary[]}`, at most 12, no cursor and no pages, `Cache-Control: no-store`. The server applies the rule once for both clients: lists by people (not the house's `tyl-editorial`, not anonymous, not under review, the author not banned) published (`publishedAt`, the first publication: republishing or editing does not move it) in the last 14 days, newest first (the newest 300 publications of the window are looked at); at least 8 cards, at least 80% of them with a picture, and a cover or at least 4 collage pictures; at most 3 lists of one author, authors taking turns (every author's newest, then every author's second, and so on, the author who published last first). **Clients** show the first **up to 4** of `lists`, in the answer's order, above the first page of `GET /lists?sort=popular`, **from 1 list** (none: Popular as before; an error here never blocks Popular), and **drop those ids from every Popular page**, the first and each «Show more». Popular's own pages and cursor are unchanged: the cursor is the last id of the server's page, not of the page shown, and a page shown shorter than 20 is fine (`nextCursor` decides). Counted as `home.fresh` when the answer had 1 or more lists. Old clients never send `fresh` and see the feed as before. The numbers are a start, to be looked at again after two or three weeks.

**`GET /lists/{id}`**: `200 ListSummary + {tiers: PublishedTier[], items: PublishedItem[], translations, picturesFrom, underReview, revision, coverAttribution?}`. `revision` (since 14.11.2026): the list's revision, **List revision** below. `coverAttribution`: the house editor's credit for the cover (**Editor's credit** below), only on a house list that has one. `picturesFrom`: the ids of the lists whose pictures this one holds copies of, as `published/{id}/{original}-{name}`; a client editing its own list sends those addresses back as they are, and copies everything else in its folder as its own photos. `404 NOT_FOUND` when there is none, or it is under review and the caller is neither staff nor its author. `underReview` says whether it is out of the feed. `awaitingApproval: true` (since 26.11.2026) when it waits for approval: it opens for everybody all the same.

**`GET /lists/mine`**: the caller's own lists, newest first, not paged: `200 {lists: (ListSummary + {authorUid, authorName, authorPhotoUrl, anonymous} as stored + {proposedSection, proposedSectionName} + boardUid? + underReview)[]}`. `underReview: true` means the list is out of the feed for moderation: its author sees it, nobody else does. `proposedSection` is the waiting proposal the list will move into, or `null`. `boardUid` is present when the publication said it. `awaitingApproval: true` (since 26.11.2026, absent otherwise) when the list waits for approval before the feed.

**`GET /lists/following`**: whom and what the caller follows: `200 {authors: {uid, name, photoUrl}[], topics: Topic[], sections: {id, followerCount}[]}`. An author with no named list left has `name: ""`.

### Publishing

**Known provenance is immutable.** When `boardUid` names a kept board with a known original (`origin.listId` or its legacy `takenFrom`), a new publication and `/lists/classify` must use that original. A conflicting body `takenFrom` is `400 {code: "INVALID", detail: "takenFrom"}`; the private lineage is checked again in the public-write transaction. The source version may advance for that same original, with fresh positional bindings. Boards with no known provenance retain the legacy path.

For card comparison, a new owned `pictureId` with no effective public `imageUrl` is a content change. Its private id/image is never returned by preflight. The same public image URL still matches the original; when both a public URL and an owned picture are supplied, the public URL wins, exactly as publication stores it. Deezer art is dropped before this decision, so a retained owned photo then is the effective new image.

**`POST /lists/classify`**: read-only publication preflight, App Check and user (guests included). Takes the same draft body as `POST /lists`, including `takenFrom`, `sourceVersion`, `boardUid` and optional `items[].sourceIndex`. Answers `200 {kind: "list", basedOn, version?}` (`basedOn` is now always `null`: a changed copy of somebody else's list is refused, below) or `200 {kind: "ranking", listId, version}`, or **`409 {code: "RANK_INSTEAD", listId}`** as `POST /lists` would answer. It writes nothing, copies no pictures, consumes no list slot and never publishes on its own. Clients use this result to name the explicit public action; `POST /lists` repeats the authoritative decision and source-version check before writing. Draft-shape refusals match publication; stale source gives `409 LIST_CHANGED`, invalid mapping/version gives `400 INVALID`. No separate criterion field exists: the list title and ordered tier labels/captions carry the current content semantics. No weekly publication quantity is enabled by default. The optional rolling policy below applies only to new independent public lists, with idempotent `boardUid` retries, Rankings, private saves and updates exempt.

**New-list quota (production: 50 a rolling week).** `PUBLIC_LISTS_PER_SEVEN_DAYS` unset, blank, or `off` retains the existing 50-current-list behavior and adds no rolling events or restrictions. Only an explicitly configured positive integer N enables the rolling policy, replacing the 50-current-list cap. Invalid configuration fails as `503 UNAVAILABLE` for a new independent public list; it cannot silently enable an invented number. Production sets N=50 in the tracked `functions/.env.tieryourlife`, which holds only this public number.

When enabled, each newly created independent public list consumes one event in the same Firestore transaction that creates it. Exact source copies become Rankings before the quota is considered. `POST /lists/{id}` updates, both Ranking write paths/withdrawal, private boards, preflight and editorial/house publication consume no event. A repeated `boardUid` returns its existing publication without spending, including parallel retries at a full quota. Deleting/unpublishing a list does not refund its event; publishing that board anew is a new list. Events at exactly seven days expire. Fifty older public lists do not prevent publishing again after the window. No historical public lists are migrated or counted as fresh events.

An exhausted rolling policy returns **`409 {error, code: "TOO_MANY_LISTS", retryAt}`**, with `retryAt` in epoch milliseconds and `Retry-After` in whole seconds. The existing code/status remains compatible; optional retry metadata tells updated clients when another new list may be published. There is no reservation and no event on rejection. Clients keep the private edit and explain waiting until that time; deleting a public list does not help. Existing clients whose message advises unpublishing must receive suitable wait wording before policy activation. The default-OFF current-list refusal remains unchanged and has no `retryAt`.

Rolling history uses `publishLocks/{authorUid}.publicListEvents`, bounded to live committed timestamps and shared by concurrent publication transactions. A committed timestamp ahead of the current instance's clock remains live until its own seven-day expiry; a backward clock cannot reopen a spent slot. History is retained when the policy is off, unchanged by updates/deletes/Rankings and removed by the existing account-erasure path. No new collection, rule, index, migration, client-writable setting or production clock override is introduced. Android from versionCode 483 and the website show the date from `retryAt`; older clients show their legacy wording.

**`POST /lists`**: publish a board. **`POST /lists/{id}`**: replace a list the caller published. Account, not banned. A list out of the feed (`underReview`) stays out after it is replaced, until staff dismiss its reports; the new snapshot is not kept (`reviewed` false). An author who withdraws a list while it is out of the feed is held: each list they publish or replace starts out of the feed, with a note naming the withdrawn list in the reports queue, until staff take down or dismiss the withdrawn list's reports, take down a held list, or 14 days pass. Dismissing a held list puts that one back and leaves the hold.

Body:
- `title`: string, required.
- `category`: section id, required. It must be an approved, not hidden section; or one the list already sits in (a republish keeps a section after it is hidden); or the caller's own waiting or declined proposal, in which case the list is filed under the proposal's `fileUnder` (or `other`) and, while the proposal waits, moves in when it is approved; or a merged section, followed to where it went. Else `400 {code: "INVALID", detail: "category"}`.
- `tiers`: the ranked tiers, 1–19 of `{label, caption?, colorLight, colorDark}` (the pool is not a tier here: its cards are the unranked ones). More is `400 TOO_MANY_TIERS`. A replace may keep as many as the stored list already has, when that is more than 19.
- `items`: 1–2000 of `{title?, imageUrl?, pictureId?, tierIndex?, credit?, attribution?, pictureFocus?}`. `pictureFocus` (since 15.11.2026): **CoverFocus** for the card's picture (**Cover focus**), stored on a card with a picture and returned on the card in `GET /lists/{id}`; `null` for the default; a card sent without the field keeps the focus a card of the same picture had before; out of range `400 INVALID` (`error` begins `items[].pictureFocus: `). A card needs a title or a picture. Of `attribution` (see **Picture attribution** below) only `link`, `originalUrl` and, on a card with a `pictureId`, `source: "web"` are read; the server works out the rest, except the house editor's credit (**Editor's credit** below). `tierIndex` out of range, or absent, means unranked. `pictureId` names the caller's own photograph, which is copied to `published/{listId}/` after Vision SafeSearch passes it. An address into another list's published folder (`/o/published%2F{other}%2F{name}`), from a list saved and published again, is copied into this list's own folder as `{other}-{name}` and the list points at the copy, so it outlives the original being edited or withdrawn; one whose original is already gone is left out. **Any other address** (`imageUrl`, `coverImageUrl`, `coverImageUrls`) is shown as it is only when it is catalogue art, on one of the hosts `image.tmdb.org`, `s4.anilist.co`, `images.igdb.com`, `shared.akamai.steamstatic.com`, `cdn-images.dzcdn.net`, `e-cdns-images.dzcdn.net` (Deezer's, which publishing drops anyway; see below), `covers.openlibrary.org`, `inaturalist-open-data.s3.amazonaws.com`, `static.inaturalist.org`, `commons.wikimedia.org`, `upload.wikimedia.org` and `thumb.wikimedia.org` (Wikimedia's thumbnail host: the same paths and bytes) under `/wikipedia/commons/` only (read as a card keeps them, **Commons addresses** below) (exactly these, `CATALOGUE_HOSTS`; a local Wikipedia's own uploads, such as fair-use pictures under `/wikipedia/en/`, are pictures from another site since 13.11.2026), or this list's own copy (`https://firebasestorage.googleapis.com/v0/b/{bucket}/o/published%2F{listId}%2F{name}`). Everything else is fetched by the proxy, looked at by Vision SafeSearch and copied to `published/{listId}/w-{32 hex}`, and the list points at the copy: the same address always lands on the same name, so publishing the list again with the original address, or with the copy's, fetches nothing. One that cannot be fetched (unreachable, a private address, too big, not a JPEG, PNG, GIF or WebP by its bytes, an animated GIF or WebP, whose first frame is all Vision sees, or not done in time) or that Vision answers nothing about is dropped: its card publishes without art, a cover or collage picture is left out, and the answer counts it in `droppedPictures`. The list records `picturesFrom` (those lists' ids, and theirs in turn; also read off the names of its own copies, `{original}-{name}`, so sending the copy's own addresses again keeps it): when staff take one of them down, its pictures are deleted from every copy, a copy of a copy included. An `imageUrl` or `coverImageUrl` into the caller's own folder (`/o/users%2F{uid}%2Fpictures%2F{id}`) is taken as that `pictureId` or `coverPictureId`; one into anyone else's folder is dropped, and so are own-folder addresses in `coverImageUrls`. A board kept in the account (`PUT /boards`) keeps its own-folder collage as sent.

**Copies a list stops showing** (since 20.11.2026). Publishing a list again, or a ranking's added cards again, no longer deletes the copies in `published/{listId}/` the new version does not show: they are marked retired (custom metadata `retiredAt`, epoch ms) and stay. Other people's boards, rankings and Continue entries keep a list's picture addresses, and so may a guest's board on a device. The daily `refreshPictures` deletes a retired copy 30 days after it was retired, and only when no published list, ranking, board kept in an account or Continue entry names it then (any field holding its address, in either form). A copy the list shows again loses the mark. Unpublishing, a takedown and an erased account still delete their copies at once, as before.
- `coverImageUrl`, `coverPictureId`, `coverImageUrls` (the chosen collage, up to 6): optional.
- `coverFocus`: optional **CoverFocus** for the single cover (**Cover focus**); stored only with a cover, and told in the list's summary and page while it has one. `null` is the centre; a republish without the field keeps the focus before while the cover is the same picture, so a client that does not know it cannot wipe it.
- `coverAttribution`: a house publication only, the editor's credit for the cover (**Editor's credit** below); `null` takes it off, absent keeps the one the same cover had.
- `anonymous`: since 16.11.2026 (Danylo: anonymous publishing is gone; only the house publishes without a name) a person's lists go out with their name. `true` is taken only on a republish of a list already anonymous, which stays so; on a new list or a named one it is `400 {error, code: "ANONYMOUS_GONE"}`, refused rather than ignored so nobody who asked for no name is published with theirs (an old app's switch: turn it off). `false` names a list, an anonymous one included; absent keeps what a republished list was, a new one named. Clients no longer send it. House publications are anonymous as before.
- Topic, at most one of: `topicId` (an existing topic; one merged into another means the topic it ended up at), `newTopic` (a name; reuses an approved topic of that name, or the caller's own waiting one, else proposes a new one, which holds the list in `other` until a moderator decides), or **`noTopic: true`**, which takes the topic off. Sending none of them (or `null`) on a republish keeps the list's topic while it stays in the same section, and moves it into the topic its proposal became. Two at once: `400 INVALID`.
- **Staff moves hold.** On a replace of a list staff moved (`movedByStaff`, see `POST /lists/{id}/move`), each moved field is judged on its own. A body that brings the field's `from` value, or does not bring the field at all (for the topic: none of `topicId`, `newTopic`, `noTopic`), keeps the staff's `to`. A body that brings another value, `newTopic`, or `noTopic: true` for the topic, wins, and that part of `movedByStaff` is cleared. The `topicId` in the answer is what was stored.
- `takenFrom`: the id of the list this board was copied from. For a **new** publication the server compares the real source with normalized `title`, the ordered tier labels/captions, and the multiset of cards (each card's title **and** canonical picture, including duplicate occurrences). Identical content or a mere rearrangement becomes the caller's Ranking of the original: `200 {id: <original id>, ranking: true}`. The comparison accepts the base source or **one whole official house-list language version**, with untranslated texts falling back to the base. It never mixes fields from different locales. A Russian official copy therefore remains a Ranking. Tier colors, placements, local IDs, cover, category and picture credits do not create a distinct list. **Since 14.11.2026 a copy of somebody else's list with other content (a title, card or tier-caption edit outside those versions) is not published as a list of its own: `409 {error, code: "RANK_INSTEAD", listId: <original id>}`**, nothing is written and no slot is spent. The client offers "Show in Rankings" and sends the reader's placing, with the cards they added, as `PUT /lists/{listId}/rankings/mine` (**Rankings** below). Unchanged: one's own source, a board with no source, a source that is gone (the list publishes without `basedOn`), and `POST /lists/{id}` of a list already published, which stays a list as before (copies published before 14.11.2026 included); there is no migration. A hidden foreign source is `409 LIST_CHANGED`, also if it became hidden without changing its timestamp; visibility and content are rechecked in the write transaction. A stored private board's provenance is also used when `boardUid` is supplied but the client omitted `takenFrom`.
- `sourceVersion?`: the source's `updatedAt` as read. `409 {code: "LIST_CHANGED", version?}` if it has changed or disappeared; the source is checked again in the same transaction as the public write. Older clients may omit it.
- `items[].sourceIndex?`: the card's zero-based position in that exact source snapshot's `items`. Indices require `sourceVersion` (or the kept private board's origin version). They preserve duplicate identities and row order when a new publication is a Ranking; duplicate, out-of-range or wrong-card mappings are `400 {code: "INVALID", detail: "sourceIndex"}`. Missing indices use deterministic occurrence matching for legacy clients. IDs and these hints do not decide whether the content is identical.
- **`boardUid`**: the device's own uid of the board, 1–100 characters.
- **`baseRevision?`** (since 14.11.2026, `POST /lists/{id}` and `PUT /lists/editorial/{id}`): the list's `revision` the client's copy was read at (**List revision** below). When the list now has another one, the answer is `409 {code: "LIST_CHANGED", revision}` with the revision it has, and nothing is written; checked again in the write transaction. Not a whole number from 0: `400 {code: "INVALID", detail: "baseRevision"}`. Absent or `null`: not checked, as before. Ignored on a new publication. **The same Update sent again** (since 26.11.2026): a body identical byte for byte to the one that wrote the list's current revision, read at the revision just before it, is answered `200` with that revision as the first sending was, and nothing is written; so a client that lost the answer may send it again. Any other body read at an older revision is still `409 LIST_CHANGED`.

Answers:
- `200 {id, ranking: true}`: explicit publication of an unchanged foreign list became a Ranking; no new list, topic or pictures are created and no list quota is consumed. Private board progress/choice is untouched.
- `201 {id, topicId, underReview, revision, droppedPictures?}`: a new list (`revision` 1).
- `200 {id, topicId, underReview, revision, droppedPictures?}`: `POST /lists/{id}` replaced it; `revision` is the one it now has, the client's next `baseRevision`. Since 26.11.2026 the answer comes once the list is written: the copies of it in other people's boards are credited as it now is, and its pictures it no longer names are retired, just after the answer (a server queue, retried; a change of the author's name or of anonymity is still credited before the answer). Its own photographs that did not change keep their copies (since 26.11.2026, Proxy #203), so they are not checked and copied again.
- **`droppedPictures`**: how many distinct pictures from other sites were left out (could not be fetched, were not a still JPEG, PNG, GIF or WebP, Vision answered nothing, or the 12 s ran out); absent when none were. Worth telling the author: publishing the same board again tries those ones again and fetches nothing it already has. A ranking (`{id, ranking: true}`) copies no pictures and never has it.
- `underReview: true` means the list was kept but starts out of the feed (held, or replacing a hidden list): its link answers 404 to others until staff look. Tell the author it waits for moderation.
- `awaitingApproval: true` (since 26.11.2026, absent otherwise; on `201` and `200`, also on `{existing: true}` and on a resent Update): the list is published and its link opens for everybody, but it is in no feed until staff approve it (**Approval before the feed** below). Tell the author the link can be shared now and the list reaches the feed once approved. Old clients ignore the field.
- **`200 {id, topicId, existing: true, revision}`**: this author already published this `boardUid` (on `POST /lists` only). Nothing is written and the existing list is named, even for an author at either publication limit. This is what makes a retried publish idempotent. Once that list is unpublished the same `boardUid` publishes anew.

Refusals: `403 NOT_SIGNED_IN`, `403 BANNED`, **`409 {code: "RANK_INSTEAD", listId}`** (a new publication of somebody else's list with other content, above), `409 TOO_MANY_LISTS` (also when parallel publishes would pass the limit together: all but those that fit are refused), **`400 TOO_MANY_TIERS`** (`error` names the limit), `413 TOO_LARGE` (`error` names which limit), `400 INVALID` (`error` says what), `400 TOPIC_UNAVAILABLE` (someone else's waiting topic, or a rejected or merged one), `409 TOO_MANY_PENDING_TOPICS`, `422 {code: "PICTURE_REFUSED", because: "adult" | "racy" | "violence" | "unchecked", imageUrl?}` (`unchecked` since 19.11.2026: an own photograph that is an animation, which SafeSearch sees only the first frame of, or one SafeSearch could not judge; a client that does not know it shows its usual refusal), `429 VISION_DAILY_LIMIT` (Limits) (`imageUrl`, the address as sent, when the refused picture came from another site; nothing is published and nothing is kept), `422 {code: "PICTURE_LINK_NEEDED", itemIndex}` (a house publication only: the card at `itemIndex` of `items` has a picture from another site, new to this list, without the page it was found on in `attribution.link`), `400 {code: "BAD_ATTRIBUTION", reason, itemIndex | cover: true}` (a house publication only: the editor's credit on the card at `itemIndex`, or on the cover, cannot be kept; `reason` is `NO_LICENSE`, `UNKNOWN_LICENSE`, `NO_LINK`, `BAD_LINK`, `BAD_LICENSE_URL` or `TOO_LONG`; nothing is published), **`429 WEB_PICTURES_DAILY_LIMIT`** (the pictures from other sites this publication would fetch are more than the account has left today; nothing is fetched), and for `POST /lists/{id}` `404 NOT_FOUND` and `403 NOT_YOURS`. A photograph that is missing from Storage is not a refusal: its card publishes without art.

**The author's face** (`authorPhotoUrl`, on lists and rankings) comes from the ID token's `picture`. The author's own copy in `avatars/{uid}/` (what `POST /lists/face` gives) is kept as it is while it is there; one deleted (the account's photo replaced or removed) is no face. Any other picture, a Google account photo included, is copied to `avatars/{uid}/w-{32 hex}` after SafeSearch, by the rules above, and that copy is the face; a new photo is a new copy. Since 14.11.2026 the faces already published from Google were copied the same way (`npm run copy-account-faces`). A Google account photo (`lh3.googleusercontent.com`, under `/a/` or `/a-/` only; its other paths are Drive, Photos and Blogger, anybody's pictures) that cannot be copied right now (not fetched, or past the day's fetches) stays Google's address; one refused, and any other picture not copied, is no face (`null`). A face never refuses the publication. Erasing the account deletes `avatars/{uid}/`. This holds for `POST /lists`, `PATCH /lists`, and `PUT /lists/{id}/rankings/mine`.

Words of 20 characters or more go to the Natural Language classifier. It never refuses: a doubtful board is put in the reports queue, and a very doubtful one is also taken out of the feed until someone looks.

### Reports and moderation

**`POST /lists/{id}/report`**: body `{reason, note?}`, `reason` one of `sexual`, `violence`, `hate`, `spam`, `other`, `wrong_category`. One report per person per list (a second replaces the first). `204`, also for a list already gone. `400 INVALID` for another reason; `429 REPORT_DAILY_LIMIT` past the day's new reports (Limits, since 19.11.2026). The list leaves the feed (`underReview`) on the first `sexual` report or the third report of any reason but `wrong_category`, unless staff already kept this snapshot. Reports from guests, banned accounts and accounts younger than 7 days are filed and shown to staff but do not count towards that, and never take a list out themselves. A moderator reporting a list by staff gets `403 TARGET_IS_MODERATOR` (see below).

**Staff do not judge staff.** A list whose author is the owner or a moderator, the caller's own included, is the owner's alone to report, take down (with or without a ban), dismiss or move. A moderator gets `403 {code: "TARGET_IS_MODERATOR"}` and nothing changes. This holds for an anonymous list too, so the refusal tells a moderator that its author is staff. A takedown of a list already gone judges the author its reports name. House lists (`tyl-editorial`) are nobody's, and any staff may act on them.

**`GET /lists/reports`**: staff. `200 {reports: QueuedList[]}` from the 50 newest reports, one row per list, hidden lists first: `{listId, listTitle, authorName, authorUid, authorPhotoUrl, anonymous, coverImageUrl, reasons, notes, reportCount, newestAtMs, hidden, reviewed}`. On an anonymous list (`anonymous: true`), and on a list already removed whose reports do not say it was named, only the owner is told the author; a moderator gets `authorName: ""`, `authorUid: null`, `authorPhotoUrl: null`.

**`POST /lists/{id}/takedown`**: staff. Body `{ban?}`, `ban` one of `week`, `month`, `three_months`, `six_months`, `forever` (a month is 30 days). Deletes the list and its reports, and bans the author when asked: `204`. `403 TARGET_IS_MODERATOR` for a moderator on a staff member's list.

**`POST /lists/{id}/dismiss`**: staff. Puts the list back and marks this snapshot kept, so complaints no longer hide it: `204`. A list already removed stays removed; only its reports go. `403 TARGET_IS_MODERATOR` as for takedown.

**`POST /lists/{id}/move`**: staff. Body `{topicId}` (an approved topic; the list takes its section) or `{category, topicId?: null}` (an approved section; the list keeps its topic only if that topic is in the section, and loses it when `topicId: null` is sent). `204`. `400 INVALID`, `404 NOT_FOUND`, `403 TARGET_IS_MODERATOR` for a moderator on a staff member's list. The list remembers the move as **`movedByStaff: {category?: {from, to}, topicId?: {from, to}}`** (`topicId` sides may be `null`), one entry per field that changed; `from` stays the author's value across later moves, and a move back to it drops that entry. The author's replace keeps these unless the body says otherwise (`POST /lists`, "Staff moves hold").

**`GET /lists/anonymous`**: gone since 16.11.2026 (anonymous publishing ended, #155; the admin's "Anonymous lists" tab with it, Web #210): answered `404 NOT_FOUND` as any list that is not there. The anonymous lists published before stay in `GET /lists/admin/lists` and the reports queue, the owner told their author as before.

**`GET /lists/admin/counts`**: staff. `200 {reports: n, proposals: n, awaitingApproval: n}` (`awaitingApproval` since 26.11.2026: lists waiting for approval).

**Approval before the feed** (since 26.11.2026, Danylo's decision). A new list (`POST /lists`) of an ordinary account is stored with `awaitingApproval: true` and is in no feed until staff approve it: not in `GET /lists` (New, Popular, sections, topics, search, Following), not in `?fresh=1`, not in a section's collage or the suggested authors. Its link (`GET /lists/{id}`, the website's `/l/{id}`) opens at once and its author may share it. Lists by the owner, a moderator and the house (`tyl-editorial`) never wait, and neither does a ranking. Replacing a list (`POST /lists/{id}`) never makes it wait; replacing one that still waits keeps it waiting. This is not `underReview`: SafeSearch, the wording check, reports and holds work as before and on top of it. A section's or topic's list count still counts a waiting list. Lists published before the switch have no mark and count as approved.
- The switch: Firestore `config/feedApproval` `{on: boolean}`, read at most every 30 s per instance. No document, or one that cannot be read, is on. Off, new lists go straight to the feed; lists already waiting stay in the queue until approved or taken down.

- **`POST /lists/{id}/approve`**: staff. Lets the list into the feed: `204`, also for a list that waits no more (a second click does nothing). `404 NOT_FOUND`. Writes the `auditLog` row `list.approve` with `{before: {awaitingApproval: true}, after: {awaitingApproval: false}}` and stores `approvedAt`, `approvedBy` on the list. To remove a waiting list instead: `POST /lists/{id}/takedown` with an optional `ban`, as above.
- Log: each report, each list the wording check flags, and each list put in the queue writes one `NOTICE` line with `message: "COMMUNITY_REVIEW"` and `{kind: "report" | "wording" | "approval", listId}` (no names, no text), for an alert the owner sets up.

One section's lists, under review included. `topic` is a topic id, `none` (lists without a topic) or `other` (lists whose topic is not an approved topic of the section); absent means all. `200 {lists: (ListSummary + {underReview, publishedBy, proposedSection, proposedSectionName})[], nextCursor}`; `publishedBy` is `null` to a moderator on an anonymous list. `400 {code: "INVALID", detail: "section" | "topic" | "after"}`, `409 CURSOR_GONE`.

**`GET /lists/moderators`**: staff. `200 {moderators: {uid, name, photoUrl, email?, appointedAt}[]}`; `email` goes to the owner only.

**`GET /lists/moderators/candidates?q=`**: owner. Up to 10 signed-in accounts whose name, a word of it, or e-mail starts with `q` (2 characters or more): `200 {people: {uid, name, email, photoUrl}[]}`.

### Rankings

A reader's own placing of somebody's list, kept beside it, with cards of their own added if they like. The list's author is not a ranking: with `withAuthor=1` their own placing leads the sheet.

**`GET /lists/{id}/rankings?withAuthor=1&after=`**: `200 {rankings: Ranking[], nextCursor: string | null}`, 30 a page, `Cache-Control: no-store`.
- With **`withAuthor=1`** (since 14.11.2026) the first page starts with the author's placing, one more than the 30: `isAuthor: true`, its `rows` the cards of each tier in the list's order, `arrangement` the tier of each card, `tierLabels` the list's tiers, `updatedAtMs` the list's `updatedAt`, `mine: true` when the author is reading, `likedByMe: false`. An anonymous list's has `uid: ""`, `authorName: ""`, `authorPhotoUrl: null` (its author still gets `mine: true`). `404 NOT_FOUND` when there is no such list, or it is under review and the caller is neither staff nor its author. Without the parameter there is no author entry and the list is not read, as before.
- Then the people who ranked it: **the most liked first, the newest first among equals** (ties after that by id). The caller's own is in its place by the same rule with `mine: true`, no longer first. How many likes a ranking has is never sent; `likedByMe` says whether the caller gave one. The order is worked out over the list's 2000 newest rankings; older ones beyond that are not shown.
- The website's account-less rankings are not shown and never reach a cursor.
- **Cursor:** opaque (`r2.…`), the place of the last ranking shown, so a ranking withdrawn between pages loses nobody their place. A cursor of the old kind (a ranking id or `~<seconds>.<nanoseconds>`) is `409 CURSOR_GONE`: start again from the first page.

**`PUT /lists/{id}/rankings/mine`**: account, not banned. Body `{tierLabels, rows, version?, addedCards?}` or, the old way, `{tierLabels, arrangement}`:
- `tierLabels`: 1–20 labels.
- `rows`: one array per label, each the card indexes of that tier, left to right, each card at most once; cards in no row are unranked (the pool). `0…N−1` are the list's `items` (N of them); **`N+k` is `addedCards[k]`**.
- `arrangement`: one tier index or `null` per card of the list, in the list's order. Added cards sent this way are all unranked.
- `version?`: the list's `updatedAt`; a stale one is `409 LIST_CHANGED`, checked again in the write transaction. Omission remains accepted for older clients.
- **`addedCards?`** (since 14.11.2026): up to 50 cards of the reader's own, each `{title?, imageUrl?, pictureId?, attribution?, credit?}` read exactly as a card of `POST /lists` (a title or a picture; `tierIndex` and `sourceIndex` are not read, the card's place is in `rows`; an editor's credit is the house's alone and is not read). Their pictures are copied into the ranking's own folder **`published/ranking-{listId}_{uid}/`** as a published list's are: catalogue pictures whose catalogue `config/pictureCopies` switches on, with their credit; the reader's own photos (`pictureId`) and pictures from other sites after SafeSearch (the daily limit of pictures from other sites applies); another list's copy copied again as `{other}-{name}`, recorded in the ranking's `picturesFrom`. Copies the earlier version holds are kept, and copies the new version no longer shows are retired after it is written (see **Copies a list stops showing**). A `PUT` without `addedCards` (or with `[]`) takes the added cards and their copies away.

Answer: `200 Ranking + {created: boolean}`, the ranking as stored (`mine: true`, `isAuthor: false`, `likedByMe: false`); replacing one's own ranking is idempotent, counts once on the list's `rankingCount`, and keeps the likes it was given. Refusals: `403 NOT_SIGNED_IN`, `403 BANNED`, `404 NOT_FOUND` (also under review), `409 OWN_LIST`, `409 LIST_CHANGED`, `400 {code: "INVALID", detail: "addedCards" | "tierLabels" | "rows" | "arrangement" | "version"}`, `422 {code: "PICTURE_REFUSED", because, addedIndex}` (`addedIndex`: the added card whose picture SafeSearch refused; nothing is written or kept), `429 WEB_PICTURES_DAILY_LIMIT`. A photograph missing from Storage is not a refusal: its card has no picture. A ranking published through `POST /lists` (an unchanged copy, `{id, ranking: true}`) has no added cards: it replaces them, and their copies go.

**`DELETE /lists/{id}/rankings/mine`** (Withdraw): `204`, also when there was none. The ranking goes, then the likes it was given and its folder `published/ranking-{listId}_{uid}/`; asked again, it finishes a withdrawal cut short.

**`PUT /lists/{id}/rankings/{uid}/like`**, **`DELETE /lists/{id}/rankings/{uid}/like`** (since 14.11.2026): like the ranking `{uid}` made of list `{id}`, or take the like back. No body. `200 {likedByMe: true | false}`, `Cache-Control: no-store`. Asking for what is already so changes nothing: a second `PUT` adds nothing, a `DELETE` of no like answers `false`. One like per account and ranking (`rankingLikes/{likerUid}:{listId}_{uid}`, `{rankingId, listId, uid: <liker>, rankedBy, at}`); the ranking's `likeCount` moves in the same transaction and is never sent. Refusals:
- `403 NOT_SIGNED_IN`: a guest (anonymous sign-in): offer to sign in;
- `403 BANNED` (`{error, code, until}`), as publishing;
- `404 NOT_FOUND`: no such ranking, or the list is gone or under review;
- `409 {code: "CANNOT_LIKE", detail: "own" | "author"}`: one's own ranking, or the author's placing (`{uid}` is the list's author);
- `429 {code: "LIKE_LIMIT", retryAt}` with `Retry-After`: more than 300 likes given or taken back within the hour (`likeQuota/{uid}`); asking for what is already so does not count.

Erasing an account takes its likes off the counts, and its rankings with their likes and folders (`DELETE /boards/account`).

**`GET /lists/topics?q=&section=&limit=&cursor=`**: approved topics. With `q`: those whose names in any language hold every word, most followed first, one page, `nextCursor: null`. Without: biggest first (`listCount`), within `section` if given. `limit` 1–50, default 20. **Cursor:** `"<listCount>:<id>"`, passed back as `cursor`. `200 {topics: Topic[], nextCursor}`.

**`GET /lists/topics/mine`**: what the caller proposed, waiting ones first: `200 {topics: Topic[]}`.

**`GET /lists/topics/pending`**: staff. Oldest first: `200 {topics: (Topic + {proposerName, requestedSection, similar: Topic[]})[]}`. **`GET /lists/topics/{id}`**: `200 Topic`. `400 INVALID`, `404 NOT_FOUND`.

**`POST /lists/topics`**: staff. Body `{name, section, names?, pictureId?, pictureAttribution?, pictureFocus?}`: an approved topic outright, in an open section. `names` (since 14.11.2026): its translations at once, as `PATCH` takes them, `{<locale>: <name>}` for the locales of **Locales** (`en` is `name`); an empty one is left out; found by search in every language as the name is. `201 Topic`. `400 {code: "INVALID", detail: "name" | "section" | "names"}`, `409 {code: "NAME_TAKEN", id, detail: id}`, `400 BAD_PICTURE`.

Body `{name?, names?, pictureId?, pictureAttribution?, pictureFocus?}` (`pictureId: null` removes the picture). `names` is laid over the stored translations language by language (since 15.11.2026): each language sent replaces its translation, one sent `""` or `null` removes it, and every language not sent stays, so `{names: {de: "Pixar-Filme"}}` changes German alone. `pictureFocus` (**Cover focus**, since 15.11.2026) is which part of the picture shows, `null` for the centre; it stays while the picture does, and a new picture sent without one, or none, goes back to the centre. In `POST` it is kept only with a picture. `200 Topic`. `400 INVALID`, `400 BAD_PICTURE`, `400 BAD_ATTRIBUTION`, `409 NAME_TAKEN`, `409 SETTLED`. A refused name or translation (since 14.11.2026): `400 {code: "INVALID", detail: "name"}`, or `400 {code: "INVALID", detail: "names", locale?}` with `locale` the first translation refused (a language not the app's, or not a proper name; absent when `names` is no object at all). `POST /lists/topics` answers a refused translation the same way.

**A topic picture's credit** (since 14.11.2026): `pictureAttribution` in `POST` and `PATCH /lists/topics`, `{author?, license, licenseUrl?, link}` (`manual: true` may be sent or left out), by the rules of the house editor's credit (**Editor's credit** below: the same licences, `link` required, an author or licence left empty read from a Commons, Flickr or iNaturalist page). `null` takes it away. It is kept while the picture stays: a new picture sent without one, or the picture taken away, takes it away too. `Topic` carries it, as stored (`manual: true`), only while the topic has a picture. Refused: `400 {code: "BAD_ATTRIBUTION", reason, detail: "pictureAttribution"}`, `reason` as for a card. **From a catalogue** (since 14.11.2026): a picture of a franchise's title (a poster, cover or game art) names no licence; a credit with no `license` and no `licenseUrl` whose `link` is that title's page is kept as the catalogue's, as a card's attribution: `{source, link, id?}`, no `manual`, any author sent dropped. Pages: TMDB `www.themoviedb.org/(movie|tv|collection)/<id>`, AniList `anilist.co/(anime|manga)/<id>`, IGDB `www.igdb.com/games/<slug>`, Steam `store.steampowered.com/app/<id>`, Open Library `openlibrary.org/works/OL…W`; https, as a browser shows them (a slug after the id, a language or another query, a trailing slash are dropped; `themoviedb.org` and `igdb.com` without `www` are taken). `id` as a card's (`tmdb:movie:11`, `anilist:269`, `steam:…`, `openlibrary:OL…W`); none for a TMDB collection or an IGDB game. Sending it back unchanged keeps it. A client shows it as a card's credit (the catalogue's name, linked). Any other page without a licence is still refused (`NO_LICENSE`).

**`DELETE /lists/topics/{id}`**: owner. Only a topic no list carries: `204`. `409 {code: "NOT_EMPTY", detail: "lists", lists}`.

**`POST /lists/topics/{id}/follow`**: account. Idempotent, approved topics only: `200 {following: true}`. `403 NOT_SIGNED_IN`, `409 TOO_MANY_FOLLOWING`, `404 NOT_FOUND`, `409 NOT_APPROVED`.

**`DELETE /lists/topics/{id}/follow`**: idempotent, `200 {following: false}`.

**`POST /lists/topics/{id}/approve`** `{section}`, **`/reject`**, **`/rename`** `{name}`: staff. **`/merge`** `{into}`: owner. `200 Topic`. `409 SETTLED`, `400 INVALID`, `404 NOT_FOUND`. A merge moves the topic's lists and followers into the target.

Repeating a dismissal answers the same.

Body `{name?, names?, icon?, tint?, rank?}`, `rank` the owner's alone. **`/decline`** `{note?}`: staff. **`/merge`** `{into}`: owner. `200 SectionView` (staff view). The same word again on a decision left unfinished finishes moving its lists. `409 SETTLED`, `409 BUILT_IN`, `400 {code: "INVALID", detail: "into"}`, `400 BAD_PICTURE`, `400 NAME_TAKEN`, `404 NOT_FOUND`.

Body `{section, name?, names?}`: the proposal becomes an approved topic in an existing section. **`POST /lists/sections/{id}/merge-into-topic`**: staff. Body `{topic}`: into an existing approved topic. Both `200 {topic: Topic | null, proposal: SectionView | null}`, and both finish a move cut short when asked again. `409 SETTLED`, `409 NAME_TAKEN {id, section}`, `400 {code: "INVALID", detail: "section" | "name" | "topic"}`, `404 NOT_FOUND`.

An approved section: `{name?, names?, icon?, rank?, hidden?, pictureId?, pictureFocus?, tint?}` (`pictureId: null` removes the picture; `tint` is `#RRGGBB`; `pictureFocus` as a topic's, `null` for the centre, back to the centre when a new picture comes without one or the picture goes; `names` laid over the stored translations as a topic's, `""` or `null` removing a language, the languages not sent kept, since 15.11.2026, here and in `/approve`). ### House lists

Lists the house publishes, stored under author `tyl-editorial`, always anonymous, read like any other list.

**`GET /lists/editorial?after=`**: staff. `200 {lists: ListSummary[], nextCursor}`; cursor is the last id; `409 CURSOR_GONE`.

**`POST /lists/editorial`**: staff. Publish body as `POST /lists`: `201 {id, topicId, revision}`. No count limit; no classifier. **Our copies first** (since 14.11.2026): a house publication (and its edit, `PUT /lists/editorial/{id}`) is written only when every catalogue picture whose licence lets us keep a copy (a Commons file, an open iNaturalist photo, **Picture attribution** below) has become our copy; a direct Wikimedia address is refused by Wikimedia to some apps. Otherwise nothing is written and the answer is `503` with `Retry-After` and `retryAt` (epoch ms): `{code: "SOURCE_BUSY", busy: ["wikimedia"], retryAt}` when Commons could not be asked about the licences, `{code: "PICTURES_NOT_COPIED", imageUrls, retryAt}` when those pictures could not be copied in time. Send the same body again at `retryAt`; a picture that keeps failing is best replaced. The copies made by an attempt that did not go through are not lost (since 15.11.2026): they wait in the shared folder `published/catalogue/` (**Catalogue pictures on a board**), and the next attempt takes them from there instead of asking Wikimedia again; one nobody uses is removed with the shared copies no board shows after seven days. A picture of another catalogue switched on for copies (**One switch per catalogue** below) never holds a publication: one not copied keeps its catalogue address and the daily upkeep copies it. Anybody else's publication is as before: a picture not copied keeps its catalogue address. The same 19 ranked tiers, `400 TOO_MANY_TIERS`.

**A house list's source** (since 15.11.2026): `listSource` in the body of `POST /lists/editorial` and `PUT /lists/editorial/{id}`, `{label, url}`: `label` what the reader sees after "Source:", 1 to `MAX_LIST_SOURCE_LABEL` (120) characters, kept on one line with its spaces tidied; `url` an https page of at most 500 characters without a login or a port. Anything else is `400 {code: "INVALID", detail: "listSource"}`. `null` takes it away; a `PUT` without the field keeps the one the list has. Every **ListSummary** (the feeds, `GET /lists/editorial`) and `GET /lists/{id}` carry it as `listSource` when the list has one; Web and Android show "Source: {label}" linked to `url` on the list's page. A person's own list (`POST /lists`) never has one: the field is not read there. Example: `listSource: {label: "Nix's fruit stream", url: "https://www.twitch.tv/videos/123456789"}`.

**`PUT /lists/editorial/{id}`**: staff. Replace: `200 {id, topicId, revision}`; `baseRevision` and `409 LIST_CHANGED` as for `POST /lists/{id}`. Its translations stay, pruned to the texts it still shows. Tiers and staff moves as for `POST /lists/{id}`.

**`DELETE /lists/editorial/{id}`**: staff. `204`.

**`PUT /lists/editorial/{id}/translations`**: staff. Body `{translations: {<locale>: {<text as written>: <text in that locale>}}}`: locales as above without `en`; the keys are the list's own title, tier labels and captions and card titles. Replaces the translations whole and keeps only those the list shows: `200 {id, translations, dropped}`. `404 NOT_FOUND` (not a house list), `400 {code: "INVALID", detail}` (`detail` like `locale:xx`, `too_many:xx`, `too_long:xx`, `not_text:xx`), `413 TOO_LARGE`.

**House translations and `names`.** A reader shows `translations[locale]?.[text] ?? text` for every text of a house list (`GET /lists/{id}` carries `translations`). Every list summary carries `names`: its title in each locale it has been translated into (empty for a list that is not the house's), so a feed card needs no second read. A copy of a house list keeps those words. Topics and sections carry `names` of their own.

An accepted translation replacement advances the list's `updatedAt`, so an origin/sourceVersion also binds the official language baseline. Publication compares the matched language version again against fresh source contents in its write transaction.

### Picture search

**Image attribution.** Commons search requests `extmetadata` and carries the supplied author/custom attribution, licence and safe source/licence links as plain text in the existing optional `credit` string. Source links use Commons page ids when available. Missing metadata adds no credit; a known attribution that cannot fit whole in 1000 characters is not offered as a new search result. Search cache shape is 12 (13.11.2026: Wikidata names kept only in `mul`, the same in every language, are read as titles; answers cached before are not served). Existing saved boards are not rewritten. Older clients that truncate this field at 200 cannot be relied on to preserve longer credits.

**Picture attribution.** Every card with a picture is stored and sent with `attribution` (**PictureAttribution**), worked out by the server at publication: its `source` from the picture's address, an iNaturalist photo's author and licence from its `credit`, a Commons file's from Commons, and the page `link` from the address where it says one (Steam, iNaturalist, AniList characters, and AniList covers by their `media/anime/` or `media/manga/` folder since 14.11.2026, Open Library editions) or else from the `attribution.link` the client sent back, kept only when it is that catalogue's own page in its one shape (`https://www.themoviedb.org/{movie|tv|person}/{id}`, `https://anilist.co/{anime|manga|character}/{id}`, `https://www.igdb.com/games/{slug}`, `https://store.steampowered.com/app/{id}`, `https://openlibrary.org/{works|books}/{id}`). A card whose picture comes from another site, or is our copy of one, gets `{source: "web", link?}`, and so does a `pictureId` card sent with `attribution.source: "web"` (a picture kept by `POST /lists/pictures/link`); `link` is the `attribution.link` sent, any https page of at most 500 characters without a login or a port, and from a client that sends no `attribution` the one the same picture had before. A person's own photograph has none. A house publication must give `link` for every picture from another site that is new to the list (`PICTURE_LINK_NEEDED`). An AniList character with an id (`anilist:c{n}`) and no page gets `https://anilist.co/character/{n}`; an anime or manga id alone names no page, as both share one numbering. Cards stored before without an AniList page are given one by `npm run anilist-links` (lists, ranking snapshots and boards; the type from AniList by id, else from the cover's folder; a dry run unless `--apply`; a list's `revision` moves, a board's revision and fingerprint do not). The old `credit` text stays as it was, for clients that show only that. A list too heavy to store with its attributions is stored without them.

**List revision** (since 14.11.2026). Every published list has `revision`, a whole number that moves on with every write to what it shows, whoever makes it: publishing and replacing it, the house's translations, staff moving it (`POST /lists/{id}/move`, and a section or topic merged or renamed under it), the daily picture refresh moving its pictures, and the maintenance scripts that fix its cards or pictures. `updatedAt` is not it: it orders "recently updated" and stands for the version a ranking was made against, so writes the author did not make leave it alone. A list stored before revisions is at 0 until its next write. A client that edits a list keeps the `revision` it read (`GET /lists/{id}`, or the answer of its last save) with its copy and sends it as `baseRevision`; on `409 LIST_CHANGED` it loads the list again instead of writing its older copy over the newer one. Takes, rankings and moderation (taking it out of the feed, putting it back) do not move it.

**Commons addresses** (since 14.11.2026). Everywhere an address is sent for publication (cards, cover and collage of `POST /lists`, `POST /lists/{id}`, the house's, a board's collage) and in `POST /lists/pictures/link`, a Commons address is kept at a width Wikimedia makes, never as the uploaded original: a file's own page (`https://commons.wikimedia.org/wiki/File:{name}`, as people copy it from the browser), `Special:FilePath/{name}` without a `width` or wider than 1280, the original (`upload.` or `thumb.wikimedia.org/wikipedia/commons/{x}/{xy}/{name}`), and a direct thumbnail (`…/thumb/…/{n}px-{name}`) at a width Wikimedia does not make (any but 20, 40, 60, 120, 250, 330, 500, 960, 1280: it answers 400 to the others) or wider than 1280 all become `https://commons.wikimedia.org/wiki/Special:FilePath/{name}?width=600`, as search hits are (Wikimedia serves its 960 px thumbnail for it). A `Special:FilePath` with a width up to 1280 (Wikimedia rounds it up to one it makes) and a direct thumbnail at a width it makes stay as sent. Copies we keep are made from the 500 px thumbnail, asked for where Wikimedia keeps it (`https://thumb.wikimedia.org/wikipedia/commons/thumb/{x}/{xy}/{name}/500px-{name}`, one request, since 15.11.2026) and through `Special:FilePath` only when it is not there; four at a time per publication, and a `429` is waited out (its `Retry-After`, or else 1, 2, 4, 8 s) while the copying window lasts.

**Editor's credit** (since 14.11.2026). On a house publication (`POST /lists/editorial`, and its edit `PUT /lists/editorial/{id}`) a card's `attribution` with `manual: true` is the editor's own credit for its picture: `{manual: true, author?, license, licenseUrl?, link}` (other fields as usual, `source: "web"` on an uploaded file). It is stored as given (spaces tidied) and marked `manual: true`, over whatever the server would work out: the card keeps its `source`, `id`, `originalUrl` and `formerUrls`, an uploaded file becomes `source: "web"`, and publishing again, the backfill and `refreshPictures` never work it out again. `link` (the page the picture stands on) is required; `license` is required and must be one of `CC0 1.0`, `CC BY {v}`, `CC BY-SA {v}` (`v` 1.0, 2.0, 2.5, 3.0 or 4.0), a Creative Commons licence ported to one country's law, `CC BY {v} {country}` or `CC BY-SA {v} {country}` (`v` 2.0, 2.5 or 3.0, the country's code in lower case, its deed `https://creativecommons.org/licenses/by-sa/2.0/de/`; since 15.11.2026: before, the country was dropped; a country word on 1.0 or 4.0, never ported, is still dropped), `Public domain`, `Copyrighted free use` (Commons' template, deed `https://commons.wikimedia.org/wiki/Template:Copyrighted_free_use`, since 15.11.2026) or `Used with permission`; spelling is free (`cc-by-sa 4.0`, `CC0`, a Creative Commons deed's address) and it is stored in that one shape, with the deed in `licenseUrl` when none was given (none for `Used with permission`). `author` ≤300, `license` ≤100, `link` and `licenseUrl` https, ≤500. When `link` is a Commons file page (`https://commons.wikimedia.org/wiki/File:{name}`), a Flickr photo (`https://www.flickr.com/photos/{user}/{id}/`) or an iNaturalist observation (`https://www.inaturalist.org/observations/{id}`) and the author or the licence is left empty, they are read from there (an iNaturalist observation's first photo); a licence read there that is not one of those is refused as `UNKNOWN_LICENSE`. A credit sent back as it is stored is kept without being read again. `attribution.manual: false` takes the editor's credit off; a card sent with no `manual` keeps the one the same picture had. The cover's is `coverAttribution` in the body, of the same shape, kept while the cover is the same picture, and returned by `GET /lists/{id}`. Since 15.11.2026 the cover may be credited to its title's catalogue page as a topic's picture can (**A topic picture's credit**): a `coverAttribution` with no `license` and no `licenseUrl` whose `link` is a TMDB, AniList, IGDB, Steam or Open Library title page is kept as `{source, link, id?}` with the link in its one shape, e.g. `{manual: true, author: "", license: "", link: "https://www.themoviedb.org/movie/603-the-matrix?language=de"}` → `{source: "tmdb", link: "https://www.themoviedb.org/movie/603", id: "tmdb:movie:603"}`. Anyone else's `manual`, and `coverAttribution`, are ignored. Refusal: `400 BAD_ATTRIBUTION` above.

**Publication attempts.** Newly copied private, external and adopted pictures use an attempt-specific `_p_UUID` suffix; filenames and URLs are opaque to clients. A refused or failed write removes only that attempt's new files. Replacing a list reuses external copies referenced by the committed snapshot without another fetch, scan or quota charge; pending files of another attempt are never a cache. Successful cleanup considers only files referenced by the previous committed snapshot. Overlapping replacements compare `updatedAt` in the final transaction: the losing request returns `409 PUBLICATION_CHANGED`, keeps the current publication intact and may be retried. **`GET /lists/pictures?q=&scope=&lang=&page=&web=&part=&section=&topic=`**: the catalogues a scope names, asked together.
- `scope`: `all` (default), `film_tv`, `anime`, `games`, `music`, `books`, `people`, `animals`. `music` asks Wikidata (pictures from Wikimedia Commons) only, and only for items that are music (a genre is named, or the item is a band, album, single, song or musical work); its tiles take photos as wide as 2:1 (3:2 before 18.11.2026), like `all` and `animals`, where the other scopes take only covers and posters, no wider than tall.
- `lang`: a BCP-47 tag like `en` or `pt-BR`; default `en`. Since 18.11.2026 a search is made and kept in the language alone, so `en-US` and `en` get one answer from one cache entry: `pt-BR` stays `pt-BR`, another `pt-*` is `pt`, `zh-*` keeps its region or script, anything else is its first part, lower-cased.
- `page`: 1–20.
- `web=1` (or `web=true`): ask the paid web search even outside `all`.
- `part=quick`: only the fast catalogues; the answer's `rest` says whether the whole search could add more Since 26.11.2026 a quick search waits at most 1.5 s for each catalogue: one that has not answered by then is left out of the quick answer, `rest` is `true` in any scope, and the whole search brings its hits (the whole search takes the answer still coming instead of asking again, and asks once more with a timeout of its own only when that request failed; the whole answer is cached, so the next quick search of the same text has them at once). In `books` the quick search asks Open Library as well (before, Wikidata alone), and Open Library is given 3 s instead of 9. Clients need no change: they already ask the whole search when `rest` is `true`.
- `section` (since 18.11.2026, optional): the list's section id, as the list carries it (`category`): `film_tv`, `anime`, `games`, `music`, `books`, `people`, `food`, `sport`, `other`, or an approved section's own id; sent whenever the list has one, whatever the scope. `topic` (optional): the list's topic id, when the client knows it. What they change is under **What the list wants** below; without them the order is as before.
- A `q` without a letter or a digit in any script (`!!!???`, emoji, punctuation) asks no catalogue and counts no search (since 18.11.2026): `200 {items: [], hasMore: false, notices: []}`, with `rest: false` for `part=quick`. Fewer than two characters is still `400 QUERY_TOO_SHORT`.

`200 {items: PictureHit[], hasMore, notices, rest?, busy?, retryAt?, searchedAs?}` (`searchedAs` since 18.11.2026, **A second attempt** below; an IGDB game's hit also carries `popularity` since 15.11.2026: the whole number of ratings IGDB counts for it, `total_rating_count`, absent when it counts none; a client may take the most rated of several near matches, the main game of a series, and one that ignores it keeps working); the first page of a search that asks IGDB also holds the ten most rated IGDB games whose name contains what was typed (`Mario`: Super Mario Bros., Odyssey…), after IGDB's own search results and without repeats, since its search ranks by text alone, `notices` holding `"webOff"` or `"webDailyLimit"`; `busy` (since 14.11.2026) names the catalogues of this search that are busy (they answered `429` or `5xx`, now or before and still resting; see below), so what they would have found is missing, and `retryAt` (epoch ms) is when all of them may be asked again. `503 {code: "SOURCE_BUSY", retryAt, busy}` with `Retry-After` (seconds): nothing was found while a catalogue the search needs is busy, so "nothing by that name" is not known; ask again at `retryAt` (a quick answer with `rest: true` is a `200`, the whole search to come). `400 QUERY_TOO_SHORT`, `502 SOURCES_DOWN` (every catalogue failed and none of them is busy). Answers are cached three days; one with a busy catalogue's gap is never kept.

**The whole search builds on the quick one.** Each catalogue's answer to a `part=quick` search is kept three days on its own; the whole search with the same `q`, `scope`, `lang` and `page` takes those answers as they are and asks only the catalogues they lack (the slow ones, and any that failed). Since 18.11.2026 the whole answer keeps the quick one's hits at its head in their order and puts what the slow catalogues add below, as a client shows them the first time, so the same search coming back from the cache (`part=quick` included) starts with the same tiles; web hits come below the catalogues' for the same reason.

**Order of hits** (since 18.11.2026, QA `qa-picture-search-2026-11-18`, stage 0). In a scope with a catalogue of its own, that catalogue's kind of picture comes first, other catalogues' after, Wikidata's last: `film_tv` movie and tv, `people` person, `anime` anime (its manga and characters after), `games` game, `music` artist and album, `books` book, `animals` animal. Within each, the title as typed first, then a title that starts so, one holding every typed word, the rest; then the catalogues taken in turn. `all` keeps the title order alone. Of games with one title (from IGDB and Steam, or IGDB's own re-releases) one is kept, the most rated by `popularity`, in the first one's place. A Wikidata item shows the first of up to three of its pictures (poster, photo, logo, collage; the preferred ones first) that fits the scope's tiles, so a panorama gives way to another picture of the same thing. Old clients get the same shape; only the order and which pictures are found change. Since 26.11.2026: in `books` a book whose title or other name is exactly what was typed comes first, before people and things, even the item Wikidata took the name to mean ("Circe" is the novel before the goddess); TMDB's films and series whose title or other name is exactly what was typed come most popular first by TMDB's `popularity`, in the places TMDB gave them ("Dune": the 2021 film, then the 1984 one, then the 1989 "Бархан" that TMDB also calls Dune). `popularity` is not sent for TMDB hits; answers cached before were dropped (`CACHE_SHAPE` 26).

**What the list wants** (since 18.11.2026, stage 1 of QA `qa-picture-search-2026-11-18`; the clients' copy of this was `_coordination/picture-search-stage1-2026-11-18/CONTRACT.md`). `scope` still decides which catalogues are asked; `section` and `topic` decide what comes first. A section with a catalogue of its own (`film_tv` … `books`, `people`) looked up in `all` puts that catalogue's kind first, as if the scope were the section's; since 25.11.2026 only when a hit of that kind matches the text (title or other name equal, starting so, or holding every word): borscht looked up in `all` on a games list is no game, so the section says nothing for that search and the order is as without one. Of hits ranked and matched alike, a person (a TMDB person, a Wikidata person, an artist) comes after a thing (since 25.11.2026), except in a `people` or `music` list and where a list holds sport. `food`, `sport`, and a section of somebody's own or (under `other`) a topic whose names tell a kind (cars, places, plants, brands, clubs, dishes, in the app's languages) put first Wikidata's things whose English description fits it ("Japanese dish", "association football club in London"), then Wikidata's other things, then the catalogues' pictures; Wikidata's things in the order its search gives them (it knows which Juventus, oak and Everest people mean: by title, a player with the alias "Juventus" would come before Juventus FC, the motorcycle maker Everest before the mountain), the catalogues' in title order: "Sushi" in a list of food is the dish, "Arsenal" in a list of sport the club. `other`, or a section whose names tell nothing, or one that is unknown: Wikidata's things first, then the catalogues'. Anywhere a section is sent, a disambiguation page, a given name or a family name goes last. Answers are kept by what the server made of `section` and `topic`, not by the ids: two food lists share one answer. A section's or topic's names are read at most every ten minutes.

**A second attempt** (since 18.11.2026). When the first page found nothing whose title or other name matches the text as typed (equal, starting so, or holding every typed word), the server searches again, at most twice, with: the text without what people add after a title ("Игра престолов 8 сезон смотреть онлайн" → "Игра престолов"; "watch online", "full movie", "season 2"…; since 25.11.2026 also a kind word at the end, and then searched as a list of that kind wants: "борщ блюдо" → "борщ" as food; "фильм", "игра", "аниме", "песня", "книга", "животное", "актёр" and the like in the app's languages), when nothing at all was found, the text as meant on the other keyboard layout (Cyrillic typed as Latin, "Ьфекшч" → "Matrix"; Latin typed as Cyrillic only on a `ru`, `uk` or `be` page), Wikipedia's spelling suggestion in the search's language, then in English ("Intersteller" → "interstellar"), and since 26.11.2026 a name typed in Cyrillic written in Latin letters as English writes names, "з" between vowels as "s" ("лализа" → "lalisa", Lisa's single "LALISA"). Since 26.11.2026 a spelling suggestion is taken only as a typo put right: at most one letter changed in a name of up to 7 letters, one in four in a longer one ("лализа" is not searched as "лариса"; this also holds for one kept before). The first of them that finds a match is the answer, what the text as typed found below it, and the answer says `searchedAs: {text, how}`, `how` one of `trimmed`, `layout`, `spelling`, `latin` (since 26.11.2026; a client shows any `how` the same way, "Showing results for {text}"); a client may show "Showing results for {text}". It is the same search: not counted again. The texts tried are kept with the search for three days, so a quick search and the whole one after it try the same and show the same first tiles. Since 19.11.2026 (QA D2, D6): only the catalogues' hits decide whether something matched, never the web's page titles; when something only like the text was found but nothing by exactly that name (title or other name, articles and Roman numbers aside), Wikipedia's spelling alone is tried and given only when it finds a catalogue hit by exactly that name ("Intersteller" in `all`, where a book called "Physics of the intersteller medium" was found → "interstellar"); and a spelling never changes a number ("1984" is not searched as "1988"), which also holds for one kept before.

**How sure** (since 18.11.2026). Every hit of a first page carries `confidence` (`high`, `medium`, `low`): how sure the server is that it is what the typed name means in this list; and, unless `high`, `doubts`, the reasons, in order. `high`: its title or `matchedName` is the typed name (without case, accents, punctuation, a leading article, or the difference between Roman and Arabic numbers: "The Matrix" = "Matrix", "Final Fantasy VII" = "Final Fantasy 7"), it is the kind the list wants (`section`, `topic` or the scope), and no other hit of that kind has the name. `medium`: the name matches but the list says nothing of what it wants (`noSection`) or another hit has the name too (`namesakes`: one of a fitting kind where the list says what it wants, any where it does not); or its title starts so or holds every typed word and it is of a fitting kind (`otherName`); or it is the first of the scope's own catalogue for a name written in another script ("Крёстный отец" on an English page, TMDB's "The Godfather": `otherName`). `low`: only the catalogue's search connects it with the name (`otherName`), it is another kind than the list holds (`otherKind`), or it is from the web (`web`). An answer of the second attempt is never `high` and has `spelling` first among its doubts. A client treats an unknown word in `doubts` as a reason it cannot name. A client that fills cards itself ("Paste a list") may take the first hit that is `high` or `medium` whatever its title, ask the person to look at each one that is not `high` (its first doubt is why), and take none when all are `low`. **`matchedName`**: the name of a hit that matches the typed text when it is not its title (Wikidata's label in another language or an alias: "Киев" finds "Kyiv"; TMDB's original title; AniList's romaji or native title; iNaturalist's matched name: "Cat" finds "Domestic Cat"); absent when the title matches or nobody says. A card keeps the name the person typed.

**Plants** (since 18.11.2026). `all` asks iNaturalist for plants (Plantae) as well as animals, `animals` still animals alone. A plant comes as `kind: "plant"`, credited and copied as its animals are.

**The web when nothing is found** (since 18.11.2026). When the first page of a search in any scope found nothing whose title or other name matches, neither as typed nor at the second attempt, the paid web search is asked once for the text as typed, and its first 5 pictures (https, big enough for a tile) come below what the catalogues did find, as `source: "web"`, `kind: "web"`, `confidence: "low"`, `doubts: ["web"]`. `all` asks the web as before, when the catalogues found fewer than 6 good hits. Each web hit's `attribution` is `{source: "web", link?}`, `link` the page the picture stands on, where the search names an https one (since 18.11.2026); a client keeps it on the card and sends it back, and publication keeps it as a picture from another site's page (**Picture attribution**). The web's pictures are kept with the search for three days, so asked again it costs nothing. A quick search of a scope without slow catalogues that found nothing says `rest: true` when the web may still add pictures, so the client asks the whole search. The second attempt's own searches never ask the web, nor does the house fill. The day's and the month's limits, `webDailyLimit` and `webOff` are as before. Without a web key on the server, nothing of this happens and the answer is as it was. The key (`SERPER_API_KEY`, set by the owner) is bound to `lists` since 18.11.2026 and never logged. When the web refuses it, a wrong key (403) or no credits left (400 "Not enough credits", or 402), the search answers as it would without the web, with the notice `webOff`, never a 5xx; the web is left alone an hour for every instance; and the alarm `PICTURE_SOURCE_DENIED` is raised with `source: "web"` and `reason: "key"` or `"credits"`. A busy web (429) rests the same hour without an alarm. In `POST /lists/pictures/batch` a name that only the web found comes as `unsure`, its `item` the web's first picture (`source: "web"`, `confidence: "low"`, `doubts: ["web"]`, `attribution.link` its page).

**The item the name means** (since 18.11.2026, stage 2 of QA `qa-picture-search-2026-11-18`). On the first page of every search (since 20.11.2026 also in `all` without `section` or `topic`), the server first works out which thing the name means and then looks for its picture. It asks Wikidata's search and Wikipedia's (in the search's language and in English) together, reads each candidate's classes, occupations, how many Wikipedias have it and its catalogue ids, and chooses the one that is a thing of the kind the list wants, found near the top and named so: an anime list's "Naruto" is the anime series, not the manga or the city; a film list's "Lion King" is the 1994 film. A Wikipedia disambiguation page, an item that says nothing of what it is, and an item found only in Wikipedia's full text without the name are never chosen; two candidates too close mean nothing is chosen. The chosen item's pictures come first: its catalogue's (TMDB asked by the item's TMDB id for a film, series or person, in a scope that asks TMDB; AniList, Steam, Open Library and iNaturalist by their ids among their hits; IGDB by name, as before), then its own picture from Commons, where Wikidata gives it a kind or the scope is `all` (an animals list keeps iNaturalist's "Octopus" above Wikidata's "Octopoda"). Their `confidence` is `high` when the choice is sure, `medium` when it is likely, never more than `medium` after a second attempt (`doubts` then start with `spelling`). Other hits keep the confidence they are judged by (**How sure**). Wikidata's hits carry a `kind` from the item's classes (`movie`, `tv`, `anime`, `manga`, `game`, `book`, `artist`, `album`, `person`; `thing` otherwise; in a music list a person who makes music is an `artist`), from a table of Wikidata's classes generated by `npm run picture-classes` and kept in `src/pictureClassTable.ts`. Nothing of the choice itself is sent. A search in `all` without `section` or `topic` (a fresh board, old clients) chooses the item too, by how well known it is and its name, a plural typed for its singular name counting as its name ("Pancakes" is Wikidata's "pancake"), and since 26.11.2026 a person's name without the Roman number of a monarch or a pope counting as a name ("Наполеон" is Napoleon I, not the town in Ohio called exactly that; "Пётр" Peter I); since 26.11.2026 too, when the best items by the name are a song or an album by one performer and none of them has a picture that fits a tile (a single's picture on Commons is a wordmark, its cover not free to show), their performer is chosen instead, `medium`, if found among the candidates with a picture ("LALISA" shows Lisa; "Gangnam Style", whose own picture shows, stays the song); where the item it chooses is a food, the rest of the answer is ranked as a Food list's: Wikidata's food first, its other things, then the catalogues' (a fresh board's "Pancakes", "Waffle", "Omelette" show the dish, not the films and games of the name). The answer's shape is unchanged.

**`POST /lists/pictures/batch`** (since 18.11.2026): a whole list's names in one request. Body `{names: string[], scope?, section?, topic?, lang?}`, 1 to 10 names (each cut to 100 characters), the other fields as in `GET /lists/pictures`. Each name is searched as that search's first page, four at a time, and counted as one search (**`429 SEARCH_LIMIT`**). `200 {results: BatchResult[]}`, one per name in the order sent: `{q, status: "found", item, searchedAs?}` when the first hit is `high` or `medium`; `{q, status: "unsure", item, searchedAs?}` with the first hit when it is `low` (a client shows it to be checked, or takes nothing); `{q, status: "none"}` when nothing was found, or the name has fewer than two characters or no letter or digit; `{q, status: "busy" | "limited", retryAt}` when a catalogue it needs is busy or the account's searches are used up; `{q, status: "later"}` when it was not begun within 16 seconds, so the answer comes inside the function's time: send it again. `item` is a **PictureHit** as `GET /lists/pictures` sends it. `400 BAD_NAMES`: no names, more than 10, or one that is not text. A client that does not use it searches name by name as before.

**A catalogue that refuses rests.** A catalogue that answers `429` or `5xx` (to its main request or a side one, such as iNaturalist's observations) is not asked by any instance until its `Retry-After` passes (seconds or an HTTP date, at most one hour), or for 5 minutes when it names none. Meanwhile it leaves a gap: the others answer as usual, the answer names it in `busy` with `retryAt`, and an answer with a gap is not kept. When nothing was found and one of them is busy, the answer is `503 SOURCE_BUSY` (above); `502 SOURCES_DOWN` only when every catalogue failed otherwise. A `4xx` about the request itself (Open Library's `422` for a short query) is no rest.

**`429 SEARCH_LIMIT`**: the account (guests too, by uid) has used its searches: 1000 in this UTC hour or 3000 this UTC day. Body `{error: "Too many picture searches", code: "SEARCH_LIMIT", retryAt}`, `retryAt` the epoch milliseconds when the full window opens again (the next UTC hour, or UTC midnight), and header `Retry-After` in whole seconds to that moment. What counts: a request that has to ask at least one catalogue and builds on no quick answer already kept, so a quick search and the whole one after it count once, a next page counts, and an answer already kept (served from the cache) counts nothing and is served even past the limit. The refusal itself is not counted, so asking again while refused does not move `retryAt`. A client should not ask again before `retryAt` (a pasted list stops looking up the titles left). A client from before this limit treats it as any refused search: the app falls back to asking TMDB and Wikidata from the phone, the website says the catalogues are down.

Outgoing requests (searches, picture downloads, `refreshPictures`) carry `User-Agent: TierYourLife/1.0 (https://tieryourlife.com/privacy)`: Wikimedia and Open Library allow more to a client that says how to reach it, and the privacy page gives the contact address. A picture download that a source answers with 429 or 5xx is tried once more after its `Retry-After` when that is at most 3 seconds (1 second when it gives none); otherwise it is `SOURCE_BUSY`, and a host that answered 429 or 503 is left alone by that instance until its `Retry-After` (5 minutes when it gives none, at most an hour). iNaturalist's observations are asked only for taxa still without an open photo after their own photos (at most 6).

**Deezer is not a picture source** (not in the first release: the right to show its covers publicly is unclear). No answer holds `source: "deezer"` or a `*.dzcdn.net` address, and answers cached before it was turned off are not served. A client must not expect `deezer` among the sources, but must still draw a card whose `imageUrl` is on `cdn-images.dzcdn.net` or `e-cdns-images.dzcdn.net`: boards kept in the account (`PUT /boards`) keep those covers as sent, and a published list may hold them until `scripts/remove-deezer-covers.ts` is run.

**Publishing and ranking drop Deezer's covers.** In `POST /lists` and `POST /lists/{id}` (and a ranking sent through them), an `imageUrl`, `coverImageUrl` or `coverImageUrls` entry on `dzcdn.net` or any of its subdomains is treated as if it had not been sent: the card is stored by its title with `imageUrl: null`, the cover and collage go without it, and when no chosen collage picture is left `previewImages` is the first cards' art, as usual. Such a card is never refused for having no picture, nothing is fetched or copied, and it is not counted in `droppedPictures`. For telling whether a board is a ranking of a list, a Deezer cover counts as no picture, so the card is matched by its title.

**`POST /lists/pictures/link`**: account (a guest gets `403 NOT_SIGNED_IN`). Body `{url, link?, credit?}`: a card's picture by its address, with the page it was found on (`link`, https, at most 500 characters) and whom to credit (`credit`, cleaned like a card's). A catalogue's own address (see `CATALOGUE_HOSTS` above) is not fetched or counted: `200 {imageUrl, attribution, credit?}`, `imageUrl` the address as it is (a Commons address as a card keeps it, **Commons addresses** below) and `attribution` the catalogue's, with its page where the address says one or the `link` sent is that catalogue's own page (a Commons file also gets its author and licence). **iNaturalist** (since 15.11.2026): its API has no lookup by photo id, so a photo's author and licence come from its observation. An observation page sent as `url` (`https://www.inaturalist.org/observations/{id}`) stands for its photo, the first with an open licence or else the first, at its `large` address: `200 {imageUrl, attribution, credit}` with `credit` the text iNaturalist writes for that photo (`(c) Name, some rights reserved (CC BY)`) and `attribution` its author, licence and photo page; an observation that cannot be read is `422 UNREACHABLE`, one without a photo `422 NOT_A_PICTURE`. A photo's address sent without `credit` and with its observation page as `link` gets that photo's `credit` the same way (none when the observation has no such photo, or does not answer). A client keeps the `credit` answered on the card, as it does a search hit's, and publication reads the licence from it. An address alone, or a photo page `https://www.inaturalist.org/photos/{id}`, still names no author or licence. Neither is counted. Any other picture is fetched (as `/keep`: https, no private address, at most three redirects, 4 MiB, JPEG, PNG, WebP or GIF), looked at by Vision SafeSearch and kept in the caller's own folder: `200 {pictureId, attribution: {source: "web", link?}, credit?}`. Publishing looks at it again. Vision out of reach keeps the picture, and publication decides. Refusals: `400 NO_URL`; `422 {code}` with `BAD_URL`, `NOT_ALLOWED` (not https, a login or port, or a private address), `UNREACHABLE`, `NOT_A_PICTURE`, `TOO_BIG`, `BAD_LINK` (a `link` that is not such a page); `422 {code: "PICTURE_REFUSED", because}`; **`503 {code: "SOURCE_BUSY", retryAt}`** with `Retry-After` (the picture's own site answered 429 or 5xx, or asked us to slow down: worth sending again after `retryAt`; not counted, and not remembered); `429 {code: "LINK_LIMIT", retryAt}` with `Retry-After`, after 400 fetches in a UTC day or 200 in an hour (`pictureWeb/{day}/links/{uid}`). Every fetch counts, refused or not, except `SOURCE_BUSY`. The same address again on the same day answers as before without fetching or counting, while the kept picture is still there. Every answer after the request is read (`200`, the `422`s of a fetch, `PICTURE_REFUSED`, `SOURCE_BUSY`, `429`) also carries `quota: {left, limit, resetsAt}`: the fetches left today out of `limit` (400), and when the UTC day starts again, in milliseconds since the epoch. A catalogue address leaves `left` as it was. The hour's limit shows only as a `429` whose `retryAt` is before `resetsAt`.

**`GET /lists/pictures/link`**: account (a guest gets `403 NOT_SIGNED_IN`). `200 {quota: {left, limit, resetsAt}}`, the same as above, before anything is sent.

**`GET /lists/pictures/uploads[?count=n]`** (since 19.11.2026): account or guest. How many own pictures may still go to `users/{uid}/pictures/` today: `checkUpload` removes every upload past the day's limit after it lands, and the card loses its picture, so a client asks here before uploading, **once for a whole selection** (`count` = how many it is about to send, 1-100), not per picture. `200 {uploads: {used, left, limit, guest, warnAt, resetsAt}}`: `limit` 200 for a guest, 2000 for an account; `warnAt` 180 for a guest (at `used >= warnAt` the client may softly offer to sign in), `null` for an account; `resetsAt` the next UTC midnight. With `count` larger than `left`: `429 {code: "SIGN_IN_FOR_MORE_UPLOADS", retryAt, uploads}` for a guest ("Sign in to add more pictures", with sign-in), `429 {code: "UPLOAD_DAILY_LIMIT", retryAt, uploads}` for an account ("try again tomorrow"), both with `Retry-After`; nothing is counted by asking. `count` that is not a whole 1-100: `400 INVALID`. A guest who signs in keeps the uid and the day's count, with the account's limit. Old clients never ask and upload as before.

**For clients, the upload limit in short:**

| Question | Answer |
|---|---|
| Where the refusal comes | **Only before uploading**, from `GET /lists/pictures/uploads?count=n`. The upload itself (straight to Storage) cannot be answered: one past the limit is removed after it lands, its card left without a picture. Publishing does not refuse for it: a removed picture is `missing` there and its card publishes without art. |
| Codes | `429 SIGN_IN_FOR_MORE_UPLOADS` for a guest (show "Sign in to add more pictures" with sign-in), `429 UPLOAD_DAILY_LIMIT` for an account ("try again tomorrow", `retryAt`). Both carry `retryAt` (epoch ms, the next UTC midnight), `Retry-After` (seconds) and `uploads`. |
| When to ask | Once per selection, before the first file goes, with `count` = the files chosen (above 100: ask with 100, then again for the rest). Not per picture. |
| Which field says "near the limit" | `uploads.left` (what is left today) and `uploads.warnAt` (a `used` value). A guest is near when `uploads.used >= uploads.warnAt`, that is **`left <= 20` of 200**; then show a soft offer to sign in, once per selection. `warnAt` is `null` for an account: no early hint. |
| A selection that partly fits | `count > left` is the 429 for all of it; a client may upload the first `left` of them and show the refusal for the rest. |
| When the check cannot be made | Network error or `5xx`: upload as before; the server still enforces the limit. |

**`POST /lists/pictures/keep`**: account (since 19.11.2026 a guest gets `403 NOT_SIGNED_IN` before anything is fetched, as with `link`). Body `{url}`: copies a web picture into the caller's own folder, for a browser that cannot read another site's bytes. `200 {pictureId}`. `400 NO_URL`, `422 {code}` with `BAD_URL`, `KEEP_LIMIT`, `NOT_ALLOWED` (not https, or a private address), `UNREACHABLE` (a busy source included), `NOT_A_PICTURE` (only JPEG, PNG, WebP, GIF), `TOO_BIG`.

## Usage statistics

Since 20.11.2026 (stage 1: server counters, the admin answer, the client endpoint ready for stage 2). Plan: `_coordination/analytics-2026-11-20/metrics-proposal.md`.

**What is kept.** Daily sums only: UTC day, event, and one cut at a time by platform, app version, language or region. No uid, device id, advertising id, IP or address is in the statistics. Lists, topics and sections are counted per id (they are public); searches as the typed words, cleaned (below). Nothing is sold or shared.

**Where the cuts come from.**
- **Platform**: from the App Check token's app id (`…:android:…`, `…:web:…`), on every request; clients send nothing for it.
- **Version, language, region**: only when the client sends them. Optional request headers on any `lists` or `boards` call: `X-TYL-Client: android/1.4.2` (or `web/<build>`) and `X-TYL-Locale: ru-RU` (the language and region **set on the device or in the browser**, never from the IP). Without the headers a request is still counted, with no version, language or region. In a batch (below) they go in the body instead.

**Searches.** A query is lower-cased, spaces collapsed, cut to 60 characters. Not counted at all when it looks like an e-mail address, a phone number or has six or more digits in a row. Kept as daily counts for 90 days (`sweepGuests` removes older days), and the admin answer shows only queries counted **3 or more times in the period asked**.

### `POST /lists/stats` (stage 2: a client's batch)

App Check, any signed-in identity (a guest too). **Send nothing while the user has turned "Send usage statistics" off**; crash counting may have its own switch. Send at most one batch per session (when the app goes to the background, or on `pagehide` for the web), and on the next start for anything left. All fields optional except as noted:

```json
{
  "version": "1.4.2",
  "locale": "ru-RU",
  "active": { "gap": 3, "sinceFirst": 9, "firstWeek": "2026-W46" },
  "steps": ["first_launch", "first_board"],
  "features": { "game.smart.done": 1, "share.image": 2 },
  "sessions": 2,
  "crashedSessions": 0,
  "crashes": [{ "type": "IllegalStateException", "place": "BoardScreen.kt:120 render" }],
  "referrer": { "domain": "reddit.com", "utm": "post" }
}
```

- **`active`**: on the device's first batch of its **UTC day**, and only then (since 22.11.2026; before, the device's local day). The server counts `active` once per UTC day per account and platform, so a device that kept local days lost a day: east of UTC, a visit after local midnight but before UTC midnight spent the new local day's `active` on a UTC day already counted, and the rest of that local day sent none. Clients count their days as `floor(epochMillis / 86 400 000)`. `gap`: days since the previous day this device sent `active`, 1–30; **31** for the first ever day, or a gap longer than 30. `sinceFirst`: days since the first launch (0 on that day). `firstWeek`: the ISO week of the first launch, `YYYY-Www`. The device keeps its first-launch date and last active day itself; neither is sent.
- **`steps`**: each sent **once per install, ever** (the device remembers what it sent): `first_launch`, `open_list` (opened somebody's or a house list), `first_board`, `first_card`, `full_list` (a board with 5+ cards all placed), `first_game` (finished), `shared`, `signed_in`, `published`. Send `first_launch` in the same batch as the first `active`.
- **`features`**: counts since the last batch, 1–200 each, names from this list only: `session`, `game.{smart|king|bracket|losers}.{start|done}`, `share.image`, `share.link`, `picture.own`, `picture.link`, `picture.pick.{commons|tmdb|igdb|inaturalist|wikidata|deezer|anilist|openlibrary|web|other}` (the source of a picture chosen from search), `picture.pos.{1|2-3|4-10|11+}` (its place in the results), `board.tier`, `board.ranked` (a board made, by kind).
- **`sessions`, `crashedSessions`**: sessions since the last batch and how many of them ended in a crash (Android learns it on the next start).
- **`crashes`**: at most 5: exception `type` (≤80) and `place`, the top frame's class, method or file:line (≤120). No message text, no user data. The web sends `window.onerror` / `unhandledrejection` as `type` = error name, `place` = file:line of the build.
- **`referrer`** (web, first visit of a session): `domain` without `www.` and without the path, `utm` = `utm_source`. Never the full address.
- Unknown fields and names are dropped silently, so a newer client is safe with an older server.

Answers: `204` counted. `400 INVALID` not an object, or `active` malformed. `429 TOO_MANY` past 50 batches from one account on one platform in a UTC day (do not retry today).

**Against inflating the numbers.** App Check, a Firebase identity, and a gate per UTC day per account per platform: `active` counts once, each step once, `active.crashed` once, whatever the client sends. The gate is a one-way hash of day, platform and account (`statsGate/{day}/accounts/{hash}`), used for nothing else and removed by the next night's `sweepGuests`.

## `boards`

The copy of a person's boards their account keeps. Not the published list: the board itself, pool and trash included. All routes: App Check and user.

**`GET /boards?after=`**: `200 {boards: BoardIndexEntry[], next: string | null}`, ordered by uid, 100 a page; **cursor** `next` is the last uid, passed back as `after`. A guest gets `{boards: [], next: null}`, not a refusal.

**`GET /boards/{uid}`**: `200 Board`. `404 NOT_FOUND`.

**`PUT /boards/{uid}`**: account. Body: the board (below) plus `basedOn` (the revision the device worked from; the key is left out on a first write) and `deviceName?`. Answers:
- `200 {uid, revision, copies?}`: stored, `revision` one higher. `copies` (absent when none): `{[catalogueAddress]: ourAddress}`, the catalogue pictures this board now shows from our shared copies (below).
- `200 {uid, revision}` with the stored revision unchanged: the same board again (its `fingerprint` equals the stored one). This makes a retried PUT idempotent.
- `409 {code: "CONFLICT", board: Board}`: the account moved on since `basedOn` and the content differs. Nothing is merged: the device keeps both.

Refusals: `403 NOT_SIGNED_IN`, `409 TOO_MANY_BOARDS`, `413 TOO_LARGE`, `400 INVALID` (`error` says what).

Board body: `{title, displayMode?, category?, coverImageUrl?, coverPictureId?, coverImageUrls?, coverFocus?, authorName?, publishedId?, deletedAt?, fingerprint?, anonymous?, tiers, items, play?, takenFrom?, origin?, rankingChoice?, favouritedAt?, favouriteChangedAt?}`:
- `origin`: `{listId, version}`, where version is the original public list's `updatedAt` when copied. `takenFrom` is the legacy list-id alias; writing an origin also writes its matching alias. Supplied aliases must agree. Once either field names an original, its list id is immutable: rebinding to another list is `400 INVALID`, including rebinding a legacy alias to a new origin. A newer version of the same original is allowed. Metadata is private backup, including when the public source is later gone; a public write validates the actual source separately.
- `rankingChoice`: `"offered" | "private" | "ranking"`. Clients write `offered` when they first show the question after **strictly more than 30% of their own progress**, then `private` or `ranking` after the explicit decision. Any stored state suppresses another offer on reopen or after withdrawal; `offered` cannot downgrade a completed decision. This is memory of an offer/decision, **not proof of a currently public Ranking**: the actual Rankings API determines public state after withdrawal or a failed save. This field never publishes anything. Omission or explicit `null` for these three metadata fields preserves their stored values, so a legacy client or withdrawal cannot erase the choice or lineage. Guests keep the same metadata locally and transfer it on sign-in; cloud board storage remains account-only.
- `items[].sourceIndex`: optional zero-based source position bound to `origin.version`; it distinguishes duplicate cards. Omission preserves the stored index for the same item uid only while the origin id/version is unchanged; changing the origin unbinds omitted indices. Explicit `null` clears a replaced card's binding. Invalid types/ranges are `400 INVALID`. It is a mapping hint, never the public content identity.
- `tiers`: 1–20 of `{uid, position, label, caption?, colorLight, colorDark, isPool?}`, uids distinct. The 20 includes the pool: 19 ranked tiers and the pool.
- `items`: up to 2000 live cards (no `deletedAt`) plus up to 2000 in the trash, so at most 4000, of `{uid, tierUid, position, title, imageUrl?, pictureId?, source?, deletedAt?, credit?, attribution?, pictureFocus?}`; `pictureFocus` (since 15.11.2026) is the card picture's **CoverFocus** by the cover's rules: `null` clears it, absent keeps the stored one while the card has a picture, a card without a picture has none, out of range `400 INVALID` (`error` begins `items[].pictureFocus: `), in the fingerprint of a client that sends it, and `state-v1:` when kept for a writer that left it out; `attribution` (**PictureAttribution**, kept on a card with a picture, cleaned to its fields and limits; an `originalUrl` not on a catalogue is dropped) is there so a card picked on one device publishes with its page link from another. A card needs a title or a picture that is kept (a `pictureId`, or an `imageUrl` another device can fetch); a card with only a picture is stored with `title: ""`. `tierUid` must name a tier of the board; `source` is `MANUAL` (default), `TMDB` or `GENERATED`; `pictureId` is `[A-Za-z0-9_-]{1,100}`; `deletedAt` set means in the trash.
- `coverPictureId`: the owner's own photograph as the whole cover, a file in their `users/{uid}/pictures/`, by the same rule as an item's `pictureId` (`[A-Za-z0-9_-]{1,100}`; one that is not is dropped, as an item's is). `null` clears it. Absent keeps the one stored, so a writer that does not know the field cannot wipe it, unless the body has a non-null `coverImageUrl` another device can fetch, or a `coverImageUrls` collage of 2 or more: another cover was chosen, and it is cleared. In the board's fingerprint the cover term is `coverPictureId ?? coverImageUrl`, as `pictureOf` is for a card.
- `coverFocus` (since 15.11.2026): **CoverFocus** for the single cover (**Cover focus**); `null` clears it. Absent keeps the one stored while the body still has a single cover (`coverImageUrl` or `coverPictureId`), so a writer that does not know the field cannot wipe it; a writer that changes the cover sends it, `null` for the centre. A client that sends it puts it in its board fingerprint (a change of focus alone is an edit); a stored focus kept for a writer that left it out makes the fingerprint `state-v1:` as other retained state does.
- `favouritedAt`, `favouriteChangedAt` (since 23.11.2026, `_coordination/favourites-sync-2026-11-23/SPEC.md`): the star «Add to favourites», kept for the account so every device shows the same Favourites. `favouritedAt`: when the board was starred (ms), `null` once unstarred; `favouriteChangedAt`: when the star last changed (ms), on the device that changed it. Sent together: `favouriteChangedAt` a number ≥ 0, `favouritedAt` a number ≥ 0 or `null`; anything else, or `favouritedAt` without `favouriteChangedAt`, is `400 INVALID`. **The later `favouriteChangedAt` wins**: a body with an earlier one than stored keeps the stored star (the sent one on a tie), so a device that was offline cannot undo a newer star. A body without `favouriteChangedAt` (every client from before) keeps the stored star. Returned on `GET /boards/{uid}`, in a conflict's `board` and on each `GET /boards` index entry when stored; absent on a board no device has starred since. **Not an edit**: the star is never part of a fingerprint (a client's or the server's `state-v1:`/`game-v1:`) and does not touch publishing; a client keeps its `editedAt` and «Update» as they were. A star change still bumps `revision` so other devices fetch it. A device behind (`basedOn` older) whose body differs from the stored one only in the star gets `409 CONFLICT` with the stored board, never the idempotent «same board again»: it merges by the later `favouriteChangedAt` and writes again. Signed out, the star stays on the device as before.
- `play`: a game under way, `{kind: "swiss" | "hill" | "bracket" | "smart", count, seed, refine, ids, history, round, startedAt, scope?, keepTier?}`. `smart` (since 15.11.2026, `_coordination/smart-pairs-2026-11-15/SPEC.md`): the smart game, asking only about cards that could still change tier, its history within the same `MAX_PLAY_HISTORY`; the algorithm is the clients' (Web's `play-vectors.json`). Its game has one more field, `tiers` (since 15.11.2026): how many tiers it sorts the cards into, a whole number from 1 to `count`, fixed at the start like `seed` (the board's tiers then; `count` for a game kept in one tier), so a tier edited mid-game or a board not yet synced cannot give two devices different next pairs; required for `smart` (else `400 INVALID`), left out of every other kind's game, as any key a game does not have; answered after `startedAt`. `refine` is `false` for `smart` by the clients' rule. A client that does not know a kind shows no game to resume on that board and sends `play` back exactly as it came: Android 521 and 530 keep the board's game as raw JSON and write it back unchanged, so the game survives their syncs; it is replaced only when someone starts another game on that board there (a game started and left with no answer clears it, as on any board), and every other board's game is untouched. The wire still uses outcome triples and distinct ordered participant IDs, with strict bounds on counts, indices, winners, scopes and timestamps. Malformed supplied games are refused with `400 INVALID`, not silently discarded. Updated clients explicitly send `play: null` to finish/clear a game. For compatibility, omitting the field preserves an existing game that an old client cannot read (more than 64 participants or 2000 outcomes); omission still clears a small legacy game as before. Explicit clear is respected even if the board fingerprint is unchanged.

The board's 2000-live-card / 700000-byte content limits stay unchanged. Long histories may be stored internally as bounded `u16le-v1` bytes encoded in base64; old flat numeric histories remain readable. If board plus game will not fit, the game is stored privately at `accounts/{uid}/plays/{boardUid}`, with the board revision, in the same transaction. Reads and conflicts reassemble the original wire game from one consistent snapshot. Missing/corrupt auxiliary data fails visibly instead of dropping the game. Clear, board deletion and account erasure remove the auxiliary copy; board writes/deletes also read the erased-account marker inside the transaction, so a retry cannot recreate private state after erasure. A board without a game retains its previous response shape; this is no new public endpoint or client Firestore permission.

When a legacy omission preserves a large game, `fingerprint` is `game-v1:<SHA-256>` of the normalized combined board and game, excluding the opaque fingerprint itself. Upgraded clients track the remote fingerprint they actually downloaded separately from their local fingerprint. An unseen `game-v1:` fingerprint requires a full restore/conflict recovery even at an already-known revision; acknowledging only the legacy writer's incomplete local contents is not enough. Once learned, the same remote fingerprint must not cause repeated downloads. Explicit completion still clears the game and uses the client's normal full-content fingerprint.
- **`displayMode`**: `WRAP` (default, also for anything unknown), `HORIZONTAL_SCROLL`, `FLAT_RANKED`. The first builds' `RANKED` is read as `FLAT_RANKED`.

When a legacy writer omits retained origin/choice/source-index metadata, the combined fingerprint uses `state-v1:<SHA-256>` of normalized content and game. A retained large game keeps the existing `game-v1:` prefix and includes that metadata in its hash. Changes to metadata cannot hide behind an unchanged opaque client hash. Clients track the downloaded remote fingerprint separately; an unseen `state-v1:` (like `game-v1:`) requires restoration even at an acknowledged revision, while an already-learned marker must not cause a download loop. Sending the complete current metadata uses the client's ordinary full-content fingerprint.

**Catalogue pictures on a board.** A card picture (and the cover and collage) from a catalogue switched on for copies (**One switch per catalogue**) is shown from one copy shared by every board, `published/catalogue/w-{32 hex}`, named by the catalogue address, so the same poster on many boards is one file. The stored board names our address, and the card's `attribution` keeps its credit with the catalogue address in `originalUrl`; up to 40 new pictures are copied per write within 6 s, the others by the daily upkeep, and a catalogue that does not answer leaves its address. A board whose pictures would not fit 50 KB under its limit keeps the catalogue's addresses. **The board's `revision` and `fingerprint` stay the device's**: the move is not an edit, so the PUT answers `{uid, revision}` as before plus `copies`, and the upkeep and `remove-picture-copies` change a stored board's pictures in place without moving either. Example: `PUT` with `items[0].imageUrl: "https://image.tmdb.org/t/p/w500/x.jpg"` answers `{uid, revision: 4, copies: {"https://image.tmdb.org/t/p/w500/x.jpg": "https://firebasestorage.googleapis.com/v0/b/tieryourlife.firebasestorage.app/o/published%2Fcatalogue%2Fw-…?alt=media"}}`, and `GET` gives that card the second address with `attribution.originalUrl` the first. A client may put each `copies` address in place of its catalogue one (and set `originalUrl`) and send the board again as an ordinary edit; a client that ignores `copies` keeps working with the catalogue's address, which the server swaps on every write. Such a picture is published like any picture of another list's folder (its list takes a copy of its own). A shared copy no board shows for seven days is removed.

**`DELETE /boards/{uid}`**: account. Leaves a marker `{deleted: true}` with a new revision so other phones drop it too: `204`, also for none. **Why it is gone** (since 15.11.2026): `?removal=forever` when its owner deleted it for good (emptied the trash, deleted it for good: every other device deletes its copy too), `?removal=cloud` when only the account's copy goes (the back-up switched off, "Stop and delete": the other devices keep theirs). None named is `cloud`, as every client before sent; anything else is `400 {code: "INVALID", detail: "removal"}`. The marker keeps it, and `forever` is never taken back: `cloud` over a `forever` marker stays `forever`, `forever` over a `cloud` one makes it `forever`, each with a new revision. Every marker (`deleted: true`) in `GET /boards` and `GET /boards/{uid}` carries `removal: "forever" | "cloud"`, `cloud` for one from before; a live board carries none. A board changed on a device after it was removed still goes back up over the marker (`basedOn` its revision), as before.

**Begun lists** (since 18.11.2026, `_coordination/shared-continue-2026-11-18/SPEC.md`): somebody else's published lists the account began to place, kept with the account so Continue is the same on every device. Code: `functions/src/started.ts`. Stored one per list at `accounts/{uid}/started/{listId}`, no client Firestore access; in the daily backup with the rest; erased with the account. No uid in the address: every route is the caller's own begun lists only, and a list the caller has none of is `404 NOT_FOUND` whoever else began it. A guest gets `403 NOT_SIGNED_IN` on every route (a guest's begun lists stay on the device); an erased account's write `401 ACCOUNT_ERASED`. Old clients never call these routes.

**StartedList**: `{listId, updatedAt, changedAt, listVersion, itemCount, tierCount, title, picture, pictures, category, rows, labels?, poolOrder?, placed, play}`.
- `updatedAt`: the version, the server's time in ms, growing with every write of that list (`max(now, previous + 1)`). `changedAt`: when it was changed on its device (the device's clock, ms); one more than 5 minutes ahead of the server's is taken as the server's.
- `listVersion`: the published list's `updatedAt` the placing was made for, ≥ 0. `itemCount` 1–2000 and `tierCount` 1–20: the list's cards and tiers.
- `title` 1–200 (trimmed); `picture` https ≤ 2000 or `null`; `pictures` up to 3 of them; `category` 1–64 or `null`. What Continue shows it by.
- `rows`: exactly `tierCount` arrays of card positions `0..itemCount-1`, each position at most once over all rows. `labels?`: exactly `tierCount` entries, each ≤ 60 characters or `null` (the list's own word; an empty one is read as `null`). `poolOrder?`: distinct positions. `placed`: the sum of the rows' lengths, the server's.
- `play`: a game over the list, the board `play` format and rules (`readPlay`, 30 days from its last write, `null` after), with the list's own names: a card is its position in the published list's `items` as a decimal string (`"0"`, `"17"`), a tier its position in `tiers` as a string, the pool `"pool"`; any other id is `400 INVALID detail: "play"`.

**Tombstone**: `{listId, updatedAt, changedAt, removed: "discard" | "saved" | "done" | "evicted"}`, nothing else kept. Kept 30 days (`PLAY_LIFETIME_MS`) from its `updatedAt`, then removed when read.

**`GET /boards/started?since=`**: `200 {started: StartedList[], removed: Tombstone[], now}`, each newest `changedAt` first, `now` the server's time. Without `since`, everything; with it (a whole number, else `400 INVALID detail: "since"`), only those with `updatedAt > since`. A device keeps the largest `updatedAt` it has seen and sends it next time.

**`GET /boards/started/{listId}`**: `200 StartedList`, `200 Tombstone`, or `404 NOT_FOUND`. `listId` is `[A-Za-z0-9_-]{1,100}`, else `400 INVALID detail: "listId"`.

**`PUT /boards/started/{listId}`**: body: the StartedList fields but `updatedAt` and `placed`, plus `basedOn: number | null` (the `updatedAt` the device worked from; `null` when it had none: a new one, or a guest's at sign-in) and `changedAt`. It is stored when nothing is stored, when `basedOn` is the stored `updatedAt` (a Tombstone's too: that is Undo), or when its `changedAt` is later than the stored one: `200 {listId, updatedAt, placed}`. Otherwise `409 {code: "CONFLICT", started: StartedList | Tombstone}`, what is stored, for the device to take with "Updated from another device". `play` `null` or absent: no game, a stored one goes. Live lists are at most **50**: one more coming in (new, or back from a Tombstone) turns the oldest by `changedAt` into a Tombstone `evicted` in the same transaction, which every device then drops. Refusals: `400 {code: "INVALID", detail}` naming the field (`rows`, `labels`, `poolOrder`, `play`, `basedOn`, `changedAt`, `listVersion`, `itemCount`, `tierCount`, `title`, `picture`, `pictures`, `category`, `body`), `413 TOO_LARGE` over 700000 bytes (out of reach within these limits; kept as the boards' guard).

**`DELETE /boards/started/{listId}?reason=discard|saved|done&basedOn=&changedAt=`**: takes it out of Continue on every device: a Tombstone with that reason and a new version, `200 {listId, updatedAt, removed}`; also for a list never stored. `discard` is Discard or the swipe, `saved` Save my list, `done` every card placed. It lands like a PUT, with an equal `changedAt` landing too; `409 {code: "CONFLICT", started}` when `basedOn` is not the stored version and the stored list was changed later than `changedAt` (continued on another device). On a Tombstone it answers that Tombstone, `200`. No `reason` (or another) is `400 INVALID detail: "reason"`; `changedAt` absent is the server's time.

Example: `PUT /boards/started/AbCdEfGhIjKlMnOpQrSt {"basedOn":null,"changedAt":1795500000000,"listVersion":1795400000000,"itemCount":45,"tierCount":5,"title":"Game of Thrones characters","picture":null,"pictures":[],"category":"film_tv","rows":[[3,7],[1],[],[12],[]],"play":null}` → `200 {"listId":"AbCdEfGhIjKlMnOpQrSt","updatedAt":1795500000123,"placed":4}`; `DELETE …?reason=discard&basedOn=1795500000123&changedAt=1795500100000` → `200 {…,"updatedAt":1795500100200,"removed":"discard"}`; Undo is the same PUT with `"basedOn":1795500100200`.

**Settings** (since 18.11.2026, colour themes, artboards 58-59 of `qa-results/design-audit-2026-11-16/LIGHT-THEME-2026-11-18.md`): what the account chose for how the app looks, the same on the phone and the website. Code: `functions/src/settings.ts`. Stored at `accounts/{uid}/settings/appearance`, no client Firestore access; in the daily backup with the rest; erased with the account. Light or dark is not a setting here: it stays on each device. A guest gets `403 NOT_SIGNED_IN` on every route (a guest's choice stays on the device); an erased account's write `401 ACCOUNT_ERASED`. Old clients never call these routes and look as they do.

**ColourSetting**: `{name, hue, changedAt, updatedAt}`.
- `name`: `lavender` (the default and today's look: each client's own hand-made colours), `matcha`, `peach`, `sky` (fixed tables, chosen by the Designer on 19.11.2026; until then built from the hues 125, 42 and 212, which needs no migration: only the name is stored), `phone` (Android 12+: the wallpaper's colours; the website and older Android show lavender and keep the setting as it is), `custom` (built from `hue`).
- `hue`: **the person's own hue**, a whole number 0-359, or `null` when they never made one; never a ready colour's. Required with `custom`; with another name it is kept, so the slider starts there next time. A device sends the own hue it remembers with every write: choosing `sky` after an own 264 sends `{name: "sky", hue: 264}`, not sky's 220, and "Your own" then opens on 264 (QA D3, 19.11.2026). The server stores what is sent and cannot tell the two apart, so this is the clients' to keep.
- `changedAt`: when it was chosen on its device (the device's clock, ms); one more than 5 minutes ahead of the server's is taken as the server's. `updatedAt`: the server's version, `max(now, previous + 1)`.
- **A name a client does not know** (a colour added later): it shows lavender and does not write it back; the account keeps it until the person chooses again.
- **How a client builds the colours** (since 19.11.2026): Material Color Utilities `DynamicScheme` with variant TONAL_SPOT (spec 2021, contrast level 0) over five `TonalPalette.fromHueAndChroma` palettes, light and dark. **Ready colours** `matcha`, `peach`, `sky` are fixed tables: a client takes `presets.<name>.light` and `.dark` from the vectors as they are (`palettes` there says how they were made: matcha primary 136/28, neutral 138/7; peach 41/38, neutral 71/4; sky 220/36, neutral 237/9; secondary the primary hue at 16, tertiary that hue + 60 at 24, neutral variant the neutral chroma + 2). **The own colour** (`custom`): `seed = Hct.from(hue, 36, 50)` as an ARGB colour, `h = Hct.fromInt(seed).hue`; palettes primary (h, 36), secondary (h, 16), tertiary (h + 60, 24), neutral (h, 8), neutral variant (h, 10). Until 19.11.2026 the neutrals were 6 and 8, which is exactly `SchemeTonalSpot` of that seed; only the neutral tint changed. **`functions/test/theme-vectors.json`** holds the 36 roles (primary to surfaceContainerHighest) for the three ready colours and twelve own hues, light and dark, each channel within 1, and the setting values taken and refused; Web and Android copy it into their tests unchanged. `npm run theme-vectors` makes it with `@material/material-color-utilities` 0.3.0, and the Proxy's tests check it is current. Tier colours S-D are the same in every colour. Each ready colour's main button (`primary`) is at least 9 CIEDE2000 from the nearest tier colour: matcha 11.0 light / 9.2 dark (C), peach 10.6 / 11.1 (S), sky 11.9 / 9.5 (D); today's lavender is 9.6 / 12.8.

**`GET /boards/settings`**: `200 {colour: ColourSetting | null, photo: PhotoSlot | null}`. `colour` is `null` when the account never chose one (the device keeps its own, lavender by default). `photo` is the account's uploaded photo (**The account's photo** under `lists`), `null` when there is none: "Your photo" is shown only when it is not `null`.

**`PUT /boards/settings/colour`**: body `{name, hue, changedAt}`. **The later change wins**: it is stored when nothing is stored or its `changedAt` is the stored one's or later, and answers `200 {...ColourSetting, landed: true}`. An earlier one is not stored and answers `200 {...ColourSetting, landed: false}` with what the account keeps, for the device to show. Refusals: `400 {code: "INVALID", detail}` naming `name` (not one of the six, case included), `hue` (not a whole 0-359, or none with `custom`), `changedAt` (not a whole number of ms above 0), or `body`. Other verbs `405`; another setting `404 NOT_FOUND`.

**When a device asks and writes**: it reads `GET /boards/settings` at start and after sign-in. It takes the account's choice when that `changedAt` is later than its own; otherwise (and when `colour` is `null`) it writes its own choice with the time the person made it, so a guest's choice goes up at sign-in only when it is the newer one. Each choice the person makes is written at once.

Example: `PUT /boards/settings/colour {"name":"custom","hue":300,"changedAt":1795500000000}` → `200 {"name":"custom","hue":300,"changedAt":1795500000000,"updatedAt":1795500000123,"landed":true}`; from another device `{"name":"sky","hue":300,"changedAt":1795499000000}` → `200 {"name":"custom","hue":300,…,"landed":false}`.

**`DELETE /boards/account`**: account. Erases the account and everything the service holds about it: `204`. A guest gets `403 NOT_SIGNED_IN`. Safe to repeat: a call after an erasure that failed halfway, or after one that finished while the token is still good, is let through and answers `204` too. The first thing it writes is **`erasedAccounts/{uid}`** `{erasedAt}`, which stays: from then on every write with that account's token is `401 ACCOUNT_ERASED` (Conventions), and `checkUpload` deletes what it uploads to Storage. Among what goes:
- its moderator role (`roles/{uid}`), so it leaves `GET /lists/moderators`;
- its begun lists and their Tombstones (`accounts/{uid}/started`, **Begun lists**), with its boards and games;
- its settings (`accounts/{uid}/settings`, **Settings**), its photo's slot among them;
- the sections and topics it proposed or made: one still waiting, declined or rejected is deleted with its pictures; an approved or merged one stays without its proposer (a section's `proposerUid` and `proposerName` become `null`, a topic's `createdBy` and `proposerName` become `""`);
- its rankings (each one off its list's `rankingCount`), the likes given to them, and their folders `published/ranking-{listId}_{uid}/`; the likes it gave (each one off its ranking's `likeCount`) and `likeQuota/{uid}`;
- since 14.11.2026, its published lists take other people's rankings of them with them (as `DELETE /lists/{id}`), and the copies of its own photographs (a picture of its own folder) that other people's lists and rankings took into theirs (`picturesFrom`, files `{original}-{pictureId}…`) are deleted, the cards that showed them showing no picture (a list's `revision` moves). Copies of catalogue pictures and pictures from other sites (`{original}-w-…`) stay. Accounts erased before are not revisited.

What stays: a ban in force when the account is erased. It is kept as **`bannedIdentities/{key}`** `{until, bannedAt}`, one document per key of the person, and nothing else about them. A key is the lower-case hex SHA-256 of the UTF-8 text `email:<address>` for the account's verified e-mail (trimmed, lower-cased), and `<provider>:<id>` for each federated sign-in (`google.com:<Google's sub>`; `firebase.identities` in an ID token, `providerData` in Auth). `password`, `email`, `anonymous` and `custom` give no key. A new account whose token gives one of these keys counts as banned until that ban's `until`. Two bans on one key keep the one that lifts last.
- The erased account's own `bans/{uid}` stays, and gains `identityKeys: string[]`, the keys it left. The `auditLog` row `{who: <uid>, role: "account", what: "ban.kept_past_erasure", target: "bans/{uid}", before: null, after: {until, keys: <how many>}, at}` records it, with no name.
- A ban staff set later on the new account (`POST /lists/{id}/takedown`) replaces the `until` of every kept record of that person, shorter or longer: the newest decision is the one in force.
- Lifting a ban (`liftBan` in `functions/src/banIdentities.ts`, for the owner's route) deletes `bans/{uid}`, every record its `identityKeys` name, and the records of the account signed in as that uid now, so the erased account's uid and the new one both lift it.
- A record whose ban ran out is deleted when it is next read, and by `sweepGuests` every day.

## Background functions

Not callable:
- `sweepGuests`: daily, deletes guest identities unused for 30 days, and `bannedIdentities` records whose `until` has passed. Since 20.11.2026 it also counts Auth accounts for the usage statistics, removes earlier days' `statsGate` and searches older than 90 days, and imports the last three days of the Crashlytics BigQuery export, waiting quietly until it exists (see **Usage statistics**).
- `sweepPictures`: daily. An own picture no kept board names (trash included) is marked `retiredAt` after its first day and deleted 30 days after the mark if still nothing names it; a board naming it again drops the mark. An account keeping the most boards it may (200) has nothing deleted, since its further boards live only on its devices (since 20.11.2026; before, such pictures went after their first day).
- `sweepSearch`: every 15 minutes, adds every language to the search keys of new lists and topics.
- `refreshPictures`: daily, keeps the catalogue pictures of published lists, ranking snapshots and the cards readers added to their rankings alive and within the catalogues' terms. IGDB covers with an `id` are asked again every day (Twitch's 24-hour rule), TMDB pictures with an `id` every 90 days (TMDB's six months), at most 150 a run; every other catalogue address is fetched once a week (HEAD, or one byte), at most 300 a run. An address that answers 404 or 410 is looked up by its card's `id` (AniList, Steam, Open Library, TMDB), and where the catalogue shows something else now, every list and ranking snapshot that shows it is moved to the new address, cover and collage too, with the old one kept in `attribution.formerUrls`; `updatedAt` stays. A catalogue that answers 429 or 5xx is left for the run and rests as for searches. **A catalogue that answers 401 or 403** from its API (our key switched off, access closed), to a search, a refresh by id, Twitch's IGDB token, Commons' file details or the `tmdb` proxy, is counted per catalogue on each instance, and the instance logs at most one ERROR line a minute per catalogue with the running count: `{severity: "ERROR", message: "PICTURE_SOURCE_DENIED", source, status, count}` (`source` one of `tmdb`, `igdb` (Twitch too), `web` (the paid web search, with `reason`: `key` or `credits`), `anilist`, `steam`, `openlibrary`, `wikimedia`, `inaturalist`, `wikidata`; the hosts that serve their pictures are not counted, as a 403 there is usually one gone picture's). IGDB's firewall answers 403 to a search text that looks like an attack (`<script>`, `javascript:`, `../`, `${jndi:`) before it reads our key; such a 403 is checked with a request without text under the same token: answered, the refusal was the text's, the search goes on without IGDB and a warning is logged, no alarm; refused as well, the alarm is raised (since 18.11.2026). Cloud Logging files both lines as errors with the fields under `jsonPayload`; this repository defines no alert policy on them. Since 14.11.2026 the project has two in Cloud Monitoring (made by the Backend chat with Danylo's leave, not deployed from here): a log-match policy on `jsonPayload.message="PICTURE_SOURCE_DENIED"` and one on `"PICTURE_ALARM"` (both `resource.type="cloud_run_revision"`, `severity>=ERROR`), each emailing Danylo at most once an hour, closed after a day without a new line. Nothing is deleted: an address with no id, or whose catalogue no longer has the picture, stays and is noted in `pictureChecks/{key}` (`{url, checkedAt, refreshedAt?, status: ok|moved|dead|gone, movedTo?}`). A ranking or a republication that sends a card's former address is matched as that card at its address now. Private boards are not moved yet.
- `houseFill`: answers picture-search jobs that `scripts/house-fill.ts` writes to `houseFillJobs`.
- `publishAfter` (since 26.11.2026): the work an Update of a published list leaves for after its answer, one job per list and revision in `publishAfterJobs` written by `lists`: every copy credited as the list now is (a later revision's job does that for it), and the copies the list no longer names retired. Tried three times, the second after 5 s and the third after 20 s more; after three failed tries it logs the ERROR line `Publish after failed` and stops, the job kept with `gaveUpAt`; the next Update of the list does both again. A job whose run stopped halfway is taken up again by `copyPicturesSoon` within a quarter of an hour. No retry policy on the function itself. A job is removed once done. No client reads or writes it.
- `warmPictures` (since 28.11.2026): after a publication or an Update, `lists` queues one job per list and revision in `pictureWarmJobs` with the `published/` bucket paths of its cards, cover and preview images that the revision before did not show (at most 300). The trigger asks the site for `https://tieryourlife.com/img/200/{path}` and `/img/400/{path}`, three at a time, 30 s each, User-Agent `TierYourLife-Proxy warm-up`, so the site has made its small copies before the first visitor. No retries; a copy not made is made on its first view. One log line `Picture warm-up {listId, revision, asked, ok, failed, failures, ms}`, then the job is deleted. Nothing in a publication waits for it or fails with it. Not queued in the emulator. Clients cannot read or write the collection.
- `checkUpload` (us-east1, beside the bucket): on every file landing in `users/{uid}/pictures/`, removes it if the account was erased (`erasedAccounts/{uid}`), if its first bytes are not JPEG, PNG, GIF or WebP, or if it is past the day's limit (the account's 2001st upload that UTC day, a guest's 201st since 19.11.2026). **PictureAttribution** `{source, author?, license?, licenseUrl?, link?, originalUrl?, id?, formerUrls?, manual?}`, every field plain text or an https address. `manual: true`: `author`, `license`, `licenseUrl` and `link` are the house editor's (**Editor's credit** above); a client shows them as it shows any other. `source`: `tmdb`, `anilist`, `igdb`, `steam`, `deezer`, `openlibrary`, `inaturalist`, `wikimedia`, `web`; a client treats any other as unknown. `author` (≤300): the person the licence asks to be named, as a name: since 14.11.2026 a Commons author comes without addresses ("Name (https://…)" keeps "Name"; an address alone gives the YouTube handle or user name it carries, "YouTube" for a channel id, the site's name for another site; a trailing " - YouTube" goes, and the "I, " of a {{self}} credit: "I, Luc Viatour" → "Luc Viatour"). Cards stored before were cleaned by `npm run commons-authors` (lists, ranking snapshots and added cards, boards; an editor's own credit untouched; a dry run unless `--apply`). `license` (≤100): `CC BY 4.0`, `CC BY-SA 4.0`, `CC0 1.0`, `Public domain`, or Commons' own short name. `licenseUrl`, `link` (≤500): the licence, and the page about the picture or its title at the source. `originalUrl`: only while `imageUrl` is our copy, the catalogue address it was copied from. `id`: the catalogue's own id for what the picture shows, as its search hit names it, in one shape per catalogue: `tmdb:{movie|tv|person}:{n}`, `anilist:{n}` (anime or manga), `anilist:c{n}` (character), `igdb:{n}`, `steam:{n}`, `openlibrary:OL{n}W` or `OL{n}M`; none for the others. Clients copy it from `PictureHit.attribution` and send it back with the card; the server keeps a sent id only when it fits the card's catalogue and the address or page says none of its own (Steam addresses, AniList character pictures and covers, and the TMDB, AniList, Steam and Open Library pages, do; then theirs is kept). `formerUrls` (at most 5, oldest first): catalogue addresses the card showed before `refreshPictures` moved it to the catalogue's new one; written only by the server, from the previous snapshot. What each catalogue gives:

| source | author | license | link | copied |
|---|---|---|---|---|
| `tmdb` | — | — | title or person page, `id` | no |
| `anilist` | — | — | anime, manga or character page, `id` | no |
| `igdb` | — | — | game page, `id` | no |
| `steam` | — | — | store page, `id` | no |
| `openlibrary` | — | — | work or edition page, `id` | no |
| `inaturalist` | observer | CC BY / CC BY-SA 4.0, CC0 1.0, Public domain | photo page | yes, when the licence is known and the photo is open-data |
| `wikimedia` | author | Commons' licence name | file page | yes, when Commons names the licence |
| `web` | — | — | — | (copied as any outside picture) |

A client shows TMDB's own notice and logo wherever any card's `source` is `tmdb`, rather than reading the host off `imageUrl`.

**Ranking** `{uid, authorName, authorPhotoUrl, arrangement, rows, tierLabels, updatedAtMs, mine, isAuthor, likedByMe, addedCards?, allRows?}`. `rows` and `arrangement` are about the list's own cards alone, which is what installed apps read. Only when the reader added cards: `addedCards` `[{title, imageUrl, attribution?, credit?}]` (stored addresses; `imageUrl` may be `null`) and `allRows`, the rows with `N+k` for `addedCards[k]`. New clients draw `allRows` when it is there, else `rows`. `isAuthor: true` only on the author's entry of `withAuthor=1`.

**Topic** `{id, name, names, section, status: "pending" | "approved" | "rejected" | "merged", listCount, followerCount, following, createdBy?, mergedInto, pictureUrl, pictureAttribution?, pictureFocus?}`. `pictureFocus` (**Cover focus**): only while there is a picture. `pictureAttribution`: the staff's credit for the picture, or the catalogue title it comes from (**A topic picture's credit** above), only while there is a picture. `createdBy` goes only to its proposer and staff, and for a topic first named by an anonymous list only to its proposer and the owner.

**SectionView** `{id, name, names, icon, pictureUrl, pictureFocus?, tint, topicBg, topicIcon, status: "approved" | "pending" | "declined" | "merged", builtIn, hidden, rank, approvedAt, listCount, lists30d, newThisWeek, followerCount, following, collage}`. Each colour is `{light, dark}`; `collage` is four picture addresses or none. `pictureFocus` (**Cover focus**) only with a `pictureUrl` the viewer is given. `listCount`, `lists30d`, `newThisWeek` and `collage` are counted from the published lists and kept up to ten minutes; since 15.11.2026 every successful call that can move a list (a publication, a change, a removal, a report or moderation verb, an editorial, topic, section or admin change) makes every instance count afresh on its next read (`config/sectionCounts` holds a change counter each counts read compares).
- Its proposer, while it is not approved, also gets `fileUnder`, `proposerUid`, `declineNote`, `mergedInto`, `mergedTopicId` and `waitingLists`.
- Staff get those and `proposerName`, `palette`, `unfinished`, `finish?`, `withdrawn`, `createdAt`, `decidedAt`, `decidedBy`, and on the queue `nameClash`: `null`, `{kind: "topic", id, name, section, sectionName}` or `{kind: "section", id, name}`.

**PictureHit** `{id: "<source>:<id>", title, subtitle, imageUrl, thumbUrl, source, kind, credit?, attribution?, popularity?, matchedName?, confidence?, doubts?}` (the last three since 18.11.2026, **How sure** above). `kind` is one of `movie`, `tv`, `person`, `anime`, `manga`, `character`, `game`, `artist`, `album`, `book`, `animal`, `plant` (since 18.11.2026), `thing`, `web`; a client shows one it does not know as it shows `thing`. A client keeps `attribution` on the card and sends it back when it publishes. **Only pictures we may copy** (since 14.11.2026): an `inaturalist` hit is a photo in `inaturalist-open-data.s3.amazonaws.com` licensed CC0, CC BY, CC BY-SA or public domain (by its credit, or else by iNaturalist's `license_code`), with `attribution.license` set; a photo on `static.inaturalist.org`, licensed NC or ND, or not at all is never offered, and a taxon whose photos are all such is left out. A `wikidata` hit (a Commons file) is offered only when Commons states its licence, given in `attribution.license`. Both pass the same test as a copy (`mayCopy`). `source` is one of `tmdb`, `anilist`, `igdb`, `steam`, `openlibrary`, `inaturalist`, `wikidata`, `web`; a client treats any other as unknown. **`thumbUrl`** (filled by every source since 25.11.2026) is a smaller copy of the same picture for the grid's tile: TMDB w342, AniList's large cover (a character's face as it is), IGDB `t_cover_big`, Steam's 300 px library cover, Open Library's `-M` cover, Commons at `Special:FilePath/{name}?width=400` (Wikidata's hits and web hits that are Commons files), iNaturalist's medium photo, and for any other web hit the search engine's own https thumbnail. A client shows `thumbUrl` in the grid and keeps `imageUrl` on the card; it is null only for a web hit without such a thumbnail, and it may equal `imageUrl` where the picture is already tile-sized. Before 25.11.2026 it was null for `anilist`, `igdb`, `steam`, `openlibrary` and `web`, so clients loaded the whole picture, up to megabytes for a web hit. A `steam` hit whose cover is Steam's `portrait.png` is offered only when that picture loads (a HEAD answered with a picture within 2 s; since 25.11.2026: Steam names it for many soundtracks, demos and DLC that have none).

**Board**: `{uid, revision, updatedAt, deviceName, deleted, fingerprint, title, displayMode, category, coverImageUrl, coverImageUrls, authorName, publishedId, deletedAt, tiers, items, anonymous?, coverPictureId?, coverFocus?, play?}`. `coverPictureId` and `coverFocus` are there only when the board has one, so a board without one reads as it always did. A game untouched for 30 days is left out.

**BoardIndexEntry**: `{uid, revision, updatedAt, deviceName, deleted, fingerprint, title, itemCount}`. `itemCount` counts the cards not in the trash.

## E2E

The website and the app run their end-to-end tests against this code in the Firebase emulators, under the project **`demo-tieryourlife`**. A `demo-` project exists nowhere: the emulators never send it anywhere real.

**What changes there, and only there.** `functions/src/emulator.ts` holds the one switch: `FUNCTIONS_EMULATOR === "true"` and every project id the runtime names (`GCLOUD_PROJECT`, `FIREBASE_CONFIG.projectId`) starts with `demo-`. Anywhere else everything behaves as in production. Under the switch:
- App Check is not asked for.
- Vision SafeSearch passes every picture, and Vision colours find none, so sections get neutral colours.
- The Natural Language classifier finds nothing.
- Picture search answers `{items: [], hasMore: false, notices: []}` (and `rest: false` for `part=quick`).
- `POST /lists/pictures/keep` stores a one-pixel PNG instead of fetching, and so does publishing for each picture from another site (and a face): the list points at a copy of the one-pixel PNG.
- `tmdb` answers `{page: 1, results: [], total_pages: 0, total_results: 0}`.
- Gemini returns no image, so `generate` answers `502 GENERATION_FAILED` with the credit given back; generation is off anyway unless `OFFER_GENERATION=yes`.
- The search sweep translates nothing.
- No function declares its secrets, so the emulator never asks Secret Manager, and no key is needed.

Storage, Firestore and Auth are the emulators' own. Pictures really are copied in the Storage emulator. The addresses lists carry still name `https://firebasestorage.googleapis.com/v0/b/demo-tieryourlife.appspot.com/o/...`; to fetch one in a test, swap the origin for `http://127.0.0.1:9199`.

**Params.** `functions/.env.demo-tieryourlife` names the owner (`MODERATOR_UID=e2eOwner0001`, `MODERATOR_EMAIL=owner@e2e.test`). These are placeholders that only this project reads, so the emulators never prompt for a value. It overrides a local `functions/.env` for the demo project.

**Base URLs.** Ports are those in `firebase.json`:

| Function | URL |
|---|---|
| `lists` | `http://127.0.0.1:5001/demo-tieryourlife/europe-west1/lists` |
| `boards` | `http://127.0.0.1:5001/demo-tieryourlife/europe-west1/boards` |
| `adoptGuestCredits` | `http://127.0.0.1:5001/demo-tieryourlife/europe-west1/adoptGuestCredits` |
| `tmdb` | `http://127.0.0.1:5001/demo-tieryourlife/europe-west1/tmdb` |
| `credits`, `generate` | `http://127.0.0.1:5001/demo-tieryourlife/europe-west1/credits`, `…/generate` |
| Auth | `127.0.0.1:9099` |
| Firestore | `127.0.0.1:8080` |
| Storage | `127.0.0.1:9199` |

Routes go after the function, Hosting-style or not: `…/lists/lists/mine` and `…/lists/mine` are one route, as are `…/boards/boards/{uid}` and `…/boards/{uid}`, and `…/tmdb/tmdb/3/search/multi` and `…/tmdb/3/search/multi`.

**ID tokens from the Auth emulator.** With the Firebase JS SDK, call `connectAuthEmulator(auth, "http://127.0.0.1:9099")` and sign in as usual. Over plain HTTP, the key is not checked:
- **Guest:** `POST http://127.0.0.1:9099/identitytoolkit.googleapis.com/v1/accounts:signUp?key=demo` with body `{"returnSecureToken": true}`. The answer's `idToken` goes in `Authorization: Bearer …`.
- **Signed-in account:** the guest becomes one, keeping its uid, with `POST …/v1/accounts:update?key=demo` and body `{"idToken": "<guest token>", "email": "someone@e2e.test", "password": "…", "returnSecureToken": true}`. Or `accounts:signUp` with `email` and `password`. Use the new `idToken`.
- **Owner:** after the seed, `POST …/v1/accounts:signInWithPassword?key=demo` with the owner's e-mail and password from `functions/scripts/seed-e2e.ts`.

Publishing, follows, rankings and keeping boards need a signed-in account; a guest gets `403 NOT_SIGNED_IN`.

**Seed.** `npm --prefix functions run seed:e2e`, with the emulators running, makes:
- the owner account;
- the built-in sections (the proxy also makes them on its first read);
- one approved topic, `Studio Ghibli` in `anime`.

It prints `{owner, sections, topic}` as JSON and is safe to run again. It refuses any host but 127.0.0.1 or localhost. `E2E_FUNCTIONS_URL` and `FIREBASE_AUTH_EMULATOR_HOST` override where it calls.

**Running.**
- Interactively: `npm --prefix functions run emulators:e2e`, which builds and then runs `firebase emulators:start --only functions,firestore,auth,storage --project demo-tieryourlife`.
- **CI** runs from the repository root, with Java 11+ and `firebase-tools` installed:

  ```sh
  npm --prefix functions ci
  npm --prefix functions run emulators:e2e:exec -- "<your test command>"
  ```

  This is the build plus `firebase emulators:exec --only functions,firestore,auth,storage --project demo-tieryourlife "<your test command>"`, which starts the emulators, waits until the functions are loaded, runs the command with `FIREBASE_AUTH_EMULATOR_HOST` and `FIRESTORE_EMULATOR_HOST` set, shuts everything down, and exits with the command's status. The command runs in `functions/`. It never prompts, and needs no login, keys or Application Default Credentials. Running `npm --prefix functions run build` and then that `firebase` line from the repository root does the same.
- The proxy's own smoke test of all this: `npm --prefix functions run test:e2e` (includes default-OFF quota regression). `npm --prefix functions run test:quota:e2e` launches a separate demo-only emulator child with fixture N=2 for real rolling-quota HTTP/concurrency/expiration tests; it never edits production settings. It covers guest sign-up, refusal of a guest's publication, the guest becoming an account, publishing with an own picture, the same `boardUid` again answering `existing`, a board PUT twice and read back, the tier limit, a staff move holding against the author's republish, the withdrawal marker, every catalogue answering empty, carrying credits, and the seed twice.

**Two suites on one machine.** The ports are fixed, so only one suite runs at a time. The Storage emulator keeps its files under the system temp directory, so give a second suite its own `TEMP`/`TMP`, and its own ports in a copy of `firebase.json` passed with `--config`.

## The website's functions (tieryourlife-web/functions)

These are not the proxy. They live in the website's repository (`functions/src/web.ts`, `ranking.ts`, `pages.ts`, `og.ts`, `share.ts`, `userDeleted.ts`) and are deployed from there as the `web` function, plus the `userDeleted` trigger.

Hosting serves them at the site's own paths: `/api/**`, `/l/**`, `/r/**`, `/og/**`, `/img/**`. They read the proxy's `publishedLists/{id}` documents and write only their own:
- `rankings/{code}`;
- share cards under `share/r/{code}/` and `share/l/{id}/` in Storage, and cover collages under `share/c/{id}/` (a cache: redrawn when missing). When a list is withdrawn or taken down the proxy deletes its `share/l/{id}/` and `share/c/{id}/` with its `published/{id}/`.
- smaller copies of a published picture beside it, `published/{id}/w200/{name}` and `published/{id}/w400/{name}` (since 28.11.2026). The proxy treats such a file as its picture `{name}`: deleted with its folder, with a copy's copies when the original is taken down or erased (`discardCopiesIn`), and retired and removed with it after a republish (**Copies a list stops showing**). A name with `/` never matches a picture id, so publishing does not take one for a copy already there.

The proxy writes one document for them:
- `webCdnPurges/{auto}`: `{at: serverTimestamp, listId, reason: "takedown", paths: string[]}`, written after a takedown (`POST /lists/{id}/takedown`, also the Remove of a list waiting for approval) has deleted the list's folder and the copies others held of its pictures. `paths` are the full bucket paths of every file deleted under `published/`, the site's smaller copies among them. Then the proxy calls `POST https://tieryourlife.com/api/cdn-purge` (no body, no key; waits at most 5 s, logs `Web CDN purge call failed for {id}` otherwise). That route takes up to 50 documents without `doneAt`, removes what the site kept of their paths, clears Hosting's CDN and sets `doneAt`; with none waiting it does nothing. A document whose call failed waits for the next one. The emulator never calls the site. A list its author withdraws, an erased account and a copy no list names any more write none. A document that cannot be written is logged (`Web CDN purge for {id} not asked`) and leaves the takedown done. Clients cannot read or write the collection.

Of the proxy's data they also read, and never write:
- `publishedLists/{id}.underReview`; `publishedLists/{id}.awaitingApproval` (since 26.11.2026) may be read too: a waiting list opens by its link but belongs in no list of lists;
- `auditLog` rows with `target == "publishedLists/{id}"` and `what == "report.takedown"`, to tell a list staff took down from one its author withdrew;
- `auditLog` rows with `target == "publishedLists/{id}"` and `what == "list.withdrawn_hidden"`: its author withdrew it while it was out of the feed (`underReview`). Either of these two rows keeps a removed list's rankings hidden.
- `bans/{uid}`: `{until, bannedAt, reason, identityKeys?}`; banned while it exists and `until === null || until > now`. `identityKeys` is only on an erased account's ban.
- `bannedIdentities/{key}`: `{until, bannedAt}`, a ban kept from an erased account, by the same rule. The caller's keys come from its ID token as `DELETE /boards/account` describes; an account is banned when `bans/{uid}` or any of these says so. The proxy's reading of both is `readBan` in `functions/src/banIdentities.ts`.
- `erasedAccounts/{uid}`: `{erasedAt}`, present once the account was erased. Its ID tokens stay valid for up to an hour; the proxy refuses their writes with `401 ACCOUNT_ERASED`.

Renaming those fields or those `what` values is a change to this section, agreed with the website first.

A change to their requests or answers changes this section in the same website PR.

### Who may call
- Every `/api/**` call needs `X-Firebase-AppCheck`, exactly as in the proxy: 401 `APP_UNVERIFIED`.
- **user:** any Firebase ID token in `Authorization: Bearer`, a guest included. Without one: 401 `UNAUTHENTICATED`.
- **account:** a signed-in, non-anonymous user. A guest gets 401 `NOT_SIGNED_IN` (on `PATCH`/`DELETE /api/rank/{code}` and `GET /api/me/rankings` too).

### Rankings
A ranking is one reader's placement of a published list's cards. Its code is 8 characters, `/r/{code}` is its page, and it stores a snapshot of the list as it was ranked.

| Call | Who | Body | Answer |
|---|---|---|---|
| `POST /api/rank` | user | `{listId, rows, version?, tierLabels?}` | 201 `{code, claimToken}` |
| `GET /api/rank/{code}` | anyone; with an account's ID token, `yours` says whether it keeps it | – | 200 ranking |
| `PUT /api/rank/{code}` | user who owns it (a guest owns an unclaimed one they made) | `{rows}` | 200 `{code}`, same link |
| `PATCH /api/rank/{code}` | account | `{claimToken}` | 200 `{code}`: a guest's ranking moves to the account after sign-in |
| `DELETE /api/rank/{code}` | account that owns it | – | 204, its share cards are deleted too |
| `GET /api/me/rankings` | account | – | 200 `{rankings, more}`, newest first, at most 200 |

**Body fields**
- **`rows`:** one array per tier of the list, in the list's tier order. Each array holds card indexes in the list's `items`, in the order they were placed.
  - Each card appears at most once; cards not mentioned stay unranked.
  - At least one card must be placed.
- **`version`:** the list's `updatedAt` (millis) as the reader opened it. If the list was republished since, the answer is 409 `LIST_CHANGED` and the client offers "Load it again". A body without `version` is accepted as before, for older clients.
- **`tierLabels`:** the tier words of the arrangement the reader started from, when they started from another reader's ranking. One string per tier, each at most 40 characters.

**Refusals.** Every one is `{error, code}` with the status shown.
- 400 `INVALID`: rows don't match the tiers, a card isn't on the list, a card is placed twice, nothing is placed, or a bad `listId` or `tierLabels`.
- 404 `NOT_FOUND`: no such list or ranking.
- 409 `LIST_CHANGED`.
- 403 `BANNED` (`{error, code, until}`): an account with a ban in force, on `POST` (checked before the list is read) and `PUT`. Guests are not checked. Deleting one's own ranking stays allowed.
- 403 `NOT_YOURS`: someone else keeps it, or the claim token doesn't match.
- 409 `CLAIMED`: another account already keeps it.
- 413 `TOO_LARGE`: body over 64 KB.
- 429 `BUSY`: one save at a time per person.
- 503 `DAILY_CEILING`: the site-wide daily cap.
- 503 `UNAVAILABLE`.

**Privacy**
- Finishing a ranking never adds the reader's name or photo to the list's public Rankings. Only an explicit request in the client does that.
- A ranking outlives its list, but then it shows no author name or photo.
- When an account is deleted, `userDeleted` takes that author's name and photo out of other people's rankings of their lists (`listAuthorUid`), deletes those rankings' share cards, and leaves the account's own rankings standing without an owner (`ownerUid: null`).

### Pages and pictures
- **`GET /l/{id}`, `GET /r/{code}`:** the site's HTML shell with the page's title, description and `og:image` for chats, and the data the board needs. No auth.
- **`GET /og/l/{id}.png`, `GET /og/r/{code}.png`:** share card images, 1200×630. For house lists, `?hl=` picks the language.
- **`GET /img/{width}/{kind}/{id}/{picture}`:** a section's or topic's picture resized for a page's width.

### Under the emulators
The `web` function honours the same rule as the proxy: App Check is skipped only when `FUNCTIONS_EMULATOR === "true"` and the project id starts with `demo-`.
